## 1. `update_agent_trace` —— 冻结签名缺的是**函数**，不是参数

**来源：2026-09-27 与蔡玉礼对齐（蔡玉礼确认补充）**

### 问题

`lock_resources` / `create_order` 被调用那一刻，本次 Agent 运行**还没结束**，
`agent_trace` 注定残缺；完整的 trace 只有 `create_order` **返回之后**才存在。
而 Tool 不能直接改库（主文档 §4.3），所以必须有一个独立的 service 函数来补这次 UPDATE。
**该函数不在原冻结签名内**——不补，阶段 5 组装 trace 落库时必然撞上。

### 拍板

```
update_agent_trace(order_id, user_id, agent_trace)
```

| 项 | 约定 |
| --- | --- |
| 参数限定 | **keyword-only**（与 `create_order` 同规矩） |
| 签名含 `db` | **否**。会话与事务边界由函数自管（同 §7.1 的理由） |
| `user_id` | **必须进签名**。用于**归属校验**——否则任何调用方拿到 `orderId` 就能改别人的 trace（主文档 §5.1） |
| 失败语义 | 业务性失败返回 `ok=false`，**不抛异常**（与 `create_order` 一致） |
| 返回值 | 与 `create_order` 同构，含 `ok` |

### 时序：取方案 (a)

- **(a) ✅ 采用**：`create_order` 落 `agent_trace=None`，Agent 跑完后**由路由**调
  `update_agent_trace` 补一次 UPDATE。
- **(b) ❌ 不采用**：落残缺 trace、事后覆盖。

**为什么取 (a)**：残缺 trace 会被前端**当成完整链路渲染**，而 `TC-26` / `TC-30`
验收的恰恰是"溯源完整"；事后覆盖又存在并发窗口。`None` 的语义是干净的——
**尚未生成**，不是"生成了一半"。

### 与"冻结"的关系

**不违反冻结。** 冻的是§7 已列的五项不得改；本函数是**补缺**，不是变更。
补完将加入 `test_order_service.py` 的签名护栏，与那五项一起钉住。

## 2. `order_status` 冲突校验口径 —— 定为 `status IN (1, 2)`

**来源：2026-09-27 与蔡玉礼对齐（蔡玉礼确认）**

### 问题

`create_order` 默认 `order_status=1`（待确认），而主文档 §5.5 第 3 步字面写的是
"查询该场地在目标时段是否存在**已确认**订单"——字面只覆盖 `status=2`。
后果：**Agent 创建的待确认订单不占位**，并发下同一时段会被别人重复预约。

### 拍板

```
OCCUPYING_STATUS = (1, 2)
```

**§5.5 第 3 步的字面一并修订**，两边必须使用**逐字相同**的谓词——
否则一边拦一边放，双订照样出。修订由蔡玉礼上报集成组。

**不取"Agent 路径直接落 2"**：那样 `needConfirm=true` 就成了一句空话，
用户还没确认单就占位了。

§5.5 原文写"已确认订单"是**文档缺口，不是设计意图**——那条是给人工确认路径写的，
没预料到 Agent 路径默认落 1。

### 实测依据（双方独立复现，结果一致）

场景：`2026-10-15 13:00~17:00`，种子数据中 5 个场地各压一单
（订单 6/7/8/9/10 → 场地 2/1/3/4/5），其中订单 6（场地 2）与订单 9（场地 4）
为 `status=1`，其余 `status=2`。

对"场地 2 + 该时段"发预约，**订单 6 是该场地该时段唯一的重叠单**：

| 谓词 | 结果 |
| --- | --- |
| `status IN (2)`（§5.5 字面） | 命中 0 条 → **放行**（重复预约） |
| `status IN (1, 2)`（本口径） | 命中 `[(6, 1)]` → **拦住** |

种子数据本就是照并发场景设计的（5 场地同时段全满、status 混用），
这条 A/B 是**真实数据**上的结果，不是构造用例。

## 3. `conflictType` 取值枚举 —— 四个 snake_case

**来源：2026-09-27 与蔡玉礼对齐（蔡玉礼确认，出自 `docs/api.md` §7.2）**

阶段 3 桩里暂定的五个值是**猜的**，全部作废。准确值如下：

| 阶段 3 桩里的暂定值 | 冻结值 |
| --- | --- |
| `TIME_CONFLICT` | `time_conflict` |
| `DEVICE_NOT_FOUND` | `not_found` |
| `DEVICE_UNAVAILABLE` | `device_conflict`，且 `conflictDetail.conflicts[].reason = "status"` |
| `DEVICE_INSUFFICIENT` | `device_conflict`，且 `conflictDetail.conflicts[].reason = "exhausted"` |
| `INVALID_TIME_RANGE` | `invalid_param` |

**两条要点：**

1. 命名是 **snake_case，不是 SCREAMING_SNAKE**。
2. 设备类的两种情形**不再拆成两个取值**，统一为 `device_conflict`，
   靠 `conflictDetail.conflicts[].reason` 区分"设备停用"（`status`）
   与"数量不足"（`exhausted`）。

### 入参容错口径（一并对齐）

| 情形 | 处理 |
| --- | --- |
| `space_id` 传数字字符串 `"101"` | **转成整数**；转不了才报 `invalid_param` |
| `device_ids` 传字符串 `"1"` | **必须挡掉报错**。不挡会被当作**逐字符迭代**，静默变成 `[1]`——错得无声无息 |
| `device_ids` | **必须是数组** |

> ⚠️ **更正（黄嵩 2026-09-28，本条的目的之一就是把它写下来）**
>
> 黄嵩上一轮给出的结论是「**模块 7 单方面冻结了这份签名，主文档没提**」。
> 该结论**不成立**，根因是一次**工具层面的漏检**：
>
> - `git grep` 在 `core.quotepath` **未设置（默认 `true`）** 时，会把非 ASCII 路径
>   **转义**成八进制串再打印 —— 本机实测输出形如
>   `"docs/\345\274\200\345\217\221\346\265\201\347\250\213.md"`（即 `docs/开发流程.md`）。
> - 扫 grep 结果时，肉眼认不出那一串是哪个文件，于是**「中文名的文档 = 没被搜到」**，
>   主文档 5.3 里明明白白的 `generate_notification(order_info)` 就这样被当成了不存在。
>
> **复现方式（任选其一，均在本机验证过）**：
>
> ```bash
> git config --get core.quotepath          # 无输出 = 默认 true，即会转义
> git grep -ln "generate_notification" -- "*.md"   # → 中文路径显示成八进制串
> git -c core.quotepath=false grep -ln "generate_notification" -- "*.md"  # → 正常显示中文名
> ```
>
> **⚠️ 反过来也要说清楚**：`grep -rln "generate_notification" --include="*.md" .`
> （直接走文件系统、不经 git 路径转义）**不会**漏 —— 本机复现时它把
> `./docs/开发流程.md` 正常列了出来。所以这条不是「中文文档搜不到」的普遍规律，
> **而是「用 `git grep` 且没关 `core.quotepath` 时会漏」**。
> 两者的区别值得记住：**凡是要在仓库里找中文名文件，先 `git -c core.quotepath=false grep`，
> 或直接用文件系统 grep。**

**结论**：「延期致歉」映射到主文档 6.3 的 INT 字典中已有的值 **2（变更致歉）**，**不扩字典**。

**支撑事实（黄嵩 2026-09-28 确认）**：

| --- | --- |

- 它**不是**契约字段，两端**不需要**为它对齐枚举或版本；

- 模块 7 已按此实现并有落库断言 `notify_type == 2`。

**与第 13 号硬卡点的关系**：本分支 `app/services/notify_service.py` **仍是桩**，
