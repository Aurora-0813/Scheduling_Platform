**诊断**：`LLM_MODEL_NAME=qwen-math-turbo` 不符合本模块的使用方式。

- 该模型是**数学求解专用**模型。阿里云 Model Studio 文档对其标注：
  **最大输入长度 3072 tokens**，且 **Function Calling 一栏为「不支持」**。
- 报错文本 `Range of input length should be [1, 3072]` 正是那个输入上限。
  离线实测了组装后的请求体体积（不消耗额度、不发请求）：

  | 组成 | chars |
  | --- | --- |
  | system prompt（`build_scheduler_prompt()`） | 1953 |
  | 5 个 Tool 的 `args_schema` JSON | 4975 |
  | 用户需求原文 | 40 |
  | **合计** | **6968** |

  其中绝大多数是中文，折算 token 数已贴着 3072 的上限；而 `qwen-math-turbo`
  **即便把请求压到 3072 以内也仍然不可用**——它不支持 Function Calling，
  而本模块的全部能力都建立在「模型自选 5 个 Tool」之上。
- 失败发生在**第一个模型请求**上（`steps: 0`、0 步 trace），与「模型没按 `submit_plan`
  交方案」「`space_type` 映射错」「Tool 参数格式不对」「时间戳全相同」四类常见问题
  **都不是一回事**：那四类都要先跑通至少一次模型调用才可能发生。本次根本没跑到那一步。

**没有改动任何生产代码来「修」这次失败**——按约定，失败先报，不在拿到结论前自行调整。

### 第 ② 条未达成的原因：判定标准的前提在数据模型里不成立

这不是「模型没听话」，而是**该条标准在当前数据模型与 Prompt 下无法被任何模型达成**：

1. **设备不计费。** `device_resource` 表的字段是
   `(id, device_name, device_type, device_status, total_count, available_count, create_time, update_time)`
   ——**没有价格字段**（`docs/seed.sql:83-84` 的 INSERT 列清单可查）。
   `query_devices` 的返回值同样不含价格（见 step 2 的 observation）。
2. **场地价格就是那个 800。** 唯一与预算有关的数是 `space_resource.budget = 800.0`。
   Prompt 第 3 条写的预算规则是「场地价格超出预算时，先考虑换更便宜的场地」——
   本例 `budget` 恰好等于预算上限，**没有超**；`capacity >= 40 AND space_type = 2`
   也只命中这一个场地，没有更便宜的候选。
3. 于是「预算与设备冲突」这个前提**没有任何可计算的依据**。模型被明文禁止编造价格
   （Prompt 一·第 2 条：「绝不允许编造不存在的场地 ID、设备 ID、名称或价格」），
   它也就不可能「算」出双投影超支。
4. 模型的判断链条是自洽的：容量够 → 预算正好 → 4 台投影仪可用 → 双投影，不降级。
   它甚至把「无需降级」的理由写进了 `reason`。

**因此需要裁定的是标准的措辞，而不是模型的输出。** 三条可选路径（**不自行拍板**，见第 6 节 #1；**已于 2026-09-27 裁定为 A + C**，下表保留当时的候选与推理原文）：

| 选项 | 内容 | 需要谁定 |
| --- | --- | --- |
| A | 把场景 A 的预期改为「保住场地 + 明确说明为什么不需要降级」——因为数据模型里设备不计费，「设备超标」不可能发生 | 本模块 |
| B | 若确实要考「预算与设备冲突」，必须先给出**可计算**的依据（设备单价 / 总预算口径），Prompt 与 Tool 返回值都要带上它 | 集成组（数据模型）+ 本模块 |
| C | 换一个**真的**存在预算冲突的场景做降级用例（例如把预算压到低于唯一候选场地的价格，考「换场地 vs 降级」） | 本模块 |

按现有证据我倾向 **A + C 一起做**：A 修正这条标准的措辞，C 补一条前提成立的降级用例
——否则阶段 7 的 `AGENT-S-01` 会一直挂在一个不可达的标准上。

> **裁定结果（2026-09-27）：采纳 A + C，即上面的倾向。** A 已落进 `AGENT-S-01`
> 的断言（保住场地 + `reason` 说明无需降级）；C 落成 `AGENT-S-06` 与它的前提护栏
> `test_seed_supports_the_degradation_case`——C 在实现时**没有**用「投影仪在某时段
> 被占满」做前提，因为 `query_devices` 的签名里没有时段参数、`available_count` 也不

### 遗留 #7：时间解析接缝（2026-09-27 查清并修复，`ee91b9a`）

**两边的函数各自都对，缝在中间。**

| 位置 | 口径 |
| --- | --- |
| `app/agent/tools/lock_resources.py:121-122`（Tool 层，本模块） | 用 `_common.parse_time` 的**宽松**解析：`TIME_FORMATS` 收 4 种格式（`...HH:mm:ss` / `T...` / `...HH:mm` / 仅日期），解析前还会 `strip()` 与把 `/` 换成 `-`；**通过后把原始字符串原样传给 `create_order`** |
| `app/services/order_service.py:332-334`（模块 3，蔡玉礼分支 `feat/module3-caiyuli` 本地复刻） | `start = parse_time(start_time)` 包在 `except ValueError as exc: return _fail("invalid_param", str(exc))`；而 `parse_time`（`app/core/utils.py`）是**严格单格式** `%Y-%m-%d %H:%M:%S` |

于是这些输入是「Tool 说合法、service 说非法」：

| 模型给的 | Tool 层 | 真实 `create_order` |
| --- | --- | --- |
| `2026-09-30T14:00:00` | ✅ 通过 | ⛔ `invalid_param` |
| `2026-09-30 14:00`（无秒） | ✅ 通过 | ⛔ `invalid_param` |
| `2026/09/30 14:00:00`（斜杠） | ✅ 通过（解析时换成 `-`） | ⛔ 原始串仍带斜杠 |
| `" 2026-09-30 14:00:00 "`（带空格） | ✅ 通过（解析时 `strip()`） | ⛔ 原始串仍带空格 |

`_common.py:14-16` 的注释写的就是「真实调用里 `2026-09-30 14:00` 与 ISO 的 `2026-09-30T14:00:00` 都出现过」——所以这不是构造出来的边界，是会在演示里撞上的。

**修法（已实施，`ee91b9a`）**：Tool 层已经解析出 `start_dt` / `end_dt`，把它们用 `strftime("%Y-%m-%d %H:%M:%S")`（模块常量 `_SERVICE_TIME_FORMAT`）回写规范化再传，不再把原始串交给严格解析层。校验仍在**原文**上做（失败提示要照原样回显，模型才知道自己发了什么），只在调 `create_order` 之前换成规范格式。时机：随遗留 #3 的 (a) 裁定同批改。

> ⚠️ **仍未消除的同类隐患**：Tool 层的 `_common.parse_time`（宽松、返回 `None`、不抛异常）与服务层的 `core/utils.parse_time`（严格、抛 `ValueError`）**同名反契约**。本次回写只堵住了 `lock_resources` 这一条调用路径；并库后若有人 import 错那个同名函数，行为变化仍是静默的。**建议并库时统一命名或收敛到一处**（归集成组，未决）。

## 9. 经验与可复用产出

1. **「一次运行」的 Agent 不能做模块级缓存。** Prompt 里注入了当前时间，
   缓存住 Agent 等于把首次请求那一刻的日期钉死，服务跑过午夜之后所有相对时间
   （「今天下午」「本周五」）都会算错一天，且**不报错**，只给出一个看起来合理的错误方案。
   故 `build_agent()` 每次调用重新组装。

2. **`ChatOpenAI` 的 `api_key` 必须显式传参。** 它会隐式读取环境变量
   `OPENAI_API_KEY`，本机若存在同名变量，请求会被静默路由到别人的额度上，
   排查时极难看出。同理 `.env` 里的变量名**不用** `OPENAI_API_KEY`。

3. **假模型验不了时间戳，这件事要写在证据里而不是心里。**
   阶段 5 被单拎出来的原因就是它；用假模型跑通后如果直接标「通过」，
   等于把机制验证（保序顺延在跑）偷换成契约验证（真实间隔存在）。
