## 一、SQLite 下 BigInt 主键不会自增（应急路径会挂）

**级别**：潜在缺陷。当前不影响云库 MySQL，但会打断 §13.1 的
「云数据库断连 → 切换本地 SQLite 镜像库演示」这条应急路径。

**事实**：`app/models/` 下 9 个主键全部是裸 `BigInteger`：

```
app/models/inspection.py:17,36
app/models/notification.py:17
app/models/reservation.py:17
app/models/resource.py:18,46
app/models/system.py:18,45,60
    id: Mapped[int] = mapped_column(BigInteger, primary_key=True, autoincrement=True, ...)
```

**为什么是问题**：SQLite 只把 `INTEGER PRIMARY KEY` 当作 rowid 别名，**只有它是自增的**；
`BIGINT PRIMARY KEY` 不绑定 rowid，`autoincrement=True` 会被静默忽略。插入时不给显式 id 就会报：

```
sqlite3.IntegrityError: NOT NULL constraint failed: <table>.id
```

MySQL 下没这个问题（`BIGINT AUTO_INCREMENT` 正常），所以本地连云库时完全看不出来。

**我们踩到的经过**：模块3 原先用 `Integer` 主键，为对齐云库改成 `BigInteger` 后，
全量用例立刻从 49 通过变成 26 失败，报的就是上面这条。

**建议改法**（我们已采用）：让主键类型按方言降级

```python
from sqlalchemy import BigInteger, Integer

# MySQL 用 BIGINT 对齐云库；SQLite 降级 INTEGER 以保留自增（§13.1 应急路径）
PK_TYPE = BigInteger().with_variant(Integer, "sqlite")

id: Mapped[int] = mapped_column(PK_TYPE, primary_key=True, autoincrement=True, comment="主键")
```

已验证建表 DDL：MySQL 渲染 `id BIGINT`，SQLite 渲染 `id INTEGER`，两边行为都正确。

**依据**：通读了 `app/models/` 全部 6 个模型文件的主键定义；在本模块复现并修复后回归通过。

## 二、异步模块的覆盖率统计会虚低（加测试前需要知道）

**级别**：待发生。公用 `backend/` 目前**无 `tests/`、无 CI 配置、requirements 未声明
pytest/coverage**，所以暂未受影响。等补测试或设覆盖率门槛时才会撞上。

**事实**：`app/core/database.py` 使用了 `sqlalchemy.ext.asyncio`。

**为什么是问题**：SQLAlchemy 的异步引擎通过 **greenlet 切执行栈**在同步 ORM 与 asyncio
之间桥接，而覆盖率的追踪状态**不跨 greenlet 存活**。后果是每个协程**恰好从第一个
`await db.*` 开始丢行**——该行之前的记得到，之后全丢。

**实测数据**（模块3，同一批 67 个用例，只改这一行配置）：

| 配置 | `app/api/orders.py` | 全项目 |
|---|---|---|
| 默认 | 44% | 79% |
| `concurrency = greenlet` | 100% | 95% |

`message_service.py` 76% → 100%，`api/messages.py` 69% → 100%，同类文件一致偏低。

**判定依据**（不是猜的）：用裸 `sys.settrace` 单独跑一次请求，确认 `create_order` 的
48/50/54…86、`_order_out` 的 30–41 **全部真实触发了追踪事件**（当时的行号，函数名为
路由层私有函数 `_create_order`）——行确实执行了，只是没被 coverage 记录。
无 `await` 的函数（如 `get_current_user`）在任何配置下都是 100%，印证了是 greenlet
切栈导致的。

**建议**：补 `tests/` 的同时加 `.coveragerc`：

```ini
[run]
# greenlet：SQLAlchemy 异步引擎靠 greenlet 切栈，追踪状态不跨 greenlet 存活；
#           缺了它，所有 await 之后的行统计不到。
# thread：  只写 greenlet 会丢掉线程追踪（TestClient / uvicorn 都在自己的线程里
#           跑事件循环），表现为 lifespan、WebSocket 端点假性未覆盖。
concurrency = thread,greenlet
source = app
```

两个词缺一不可。我们实测遗漏 `thread` 时 `main.py` 报 69%，补上后 100%。

并把 `greenlet` 显式写进 requirements（它本就是 `sqlalchemy.ext.asyncio` 的运行依赖，
缺失时 import 直接失败，目前应是从别处传递进来的）。

**依据**：核实了公用 backend 无 `.coveragerc`/`pyproject`/`setup.cfg`/`tox.ini`、
无 `tests/`、无 `.github/workflows`、requirements 无测试依赖；
`app/core/database.py` 使用了 `sqlalchemy.ext.asyncio`。

## 三、`asyncmy==0.2.10` 在 Python 3.13 上装不上

**级别**：环境约束。若有人用 Python 3.13 建环境，`pip install asyncmy==0.2.10` 会直接失败。

**事实**：asyncmy 0.2.10 只发到 cp312，**没有 cp313 轮子**。pip 会退化成从源码编译，
而 Windows 上通常没有 MSVC，报的是这个（容易被误读成网络问题）：

```
ERROR: Failed to build 'asyncmy' when installing build dependencies for asyncmy
```

Python 3.11 上正常，装的是现成的 `asyncmy-0.2.10-cp311-cp311-win_amd64.whl`。

**建议**：项目统一用 **Python 3.11**（本模块已在 3.11 上验证：67→80 个用例全绿、
覆盖率 100%）。若必须用 3.13，需另配编译环境或升级 asyncmy。

**依据**：在 3.13 上 `pip install asyncmy==0.2.10 --no-deps --dry-run` 触发源码构建并失败；
在 3.11 上同一命令直接命中 cp311 轮子。

## 四、测试云库 `sys_user` 全空，但 4 张表有真外键指向它（写路径会被 1452 挡住）

**级别**：演示阻塞。凡是带用户字段的写路径——建预约、确认订单发通知、巡检、维修——
都会因外键失败而中断。

**事实**：

  `sys_user` **原本也是 0 行**（现有的 1 行是模块3 手工插的演示用户，见下）。
- 指向 `sys_user.id` 的**真外键 4 条**，与迁移 `8969262c9d0c_init_tables_single_role.py`
  第 84/101/114/127 行一致（已用云库 `information_schema.key_column_usage` 核对）：

  | 引用表 | 引用列 | 约束名 |
  |---|---|---|
  | `inspect_record` | `inspector_id` | `inspect_record_ibfk_1` |
  | `reserve_order` | `user_id` | `reserve_order_ibfk_2` |
  | `notify_message` | `receiver_id` | `notify_message_ibfk_2` |
  | `repair_ticket` | `handler_id` | `repair_ticket_ibfk_2` |

- 迁移**只建表、不灌数据**：该文件里 `INSERT` 语句 0 条。公用 `backend/` 里也没有任何

**为什么是问题**：本模块一度把 `user_id` 写成**软引用**——当时本模块不引入 `SysUser`

```

  constraint fails (`smart_scheduler_dev`.`reserve_order`,
  CONSTRAINT `reserve_order_ibfk_2` FOREIGN KEY (`user_id`) REFERENCES `sys_user` (`id`))')
```

> **2026-09-26 更正**：本条原先写作「各模块的模型**按约定**把跨模块字段声明为软引用」——
> 这句不成立。团队公用 `he/backend/app/models/` 自己就声明了真外键
> `ForeignKey("sys_user.id")`，并没有这样的约定，软引用只是本模块单方面的写法。
> 本模块已随本轮对齐改为真外键（**团队版才是与云库一致的一方**）。
> 这一更正**不改变本条的结论**：症结是云库有外键而 `sys_user` 没有种子数据，
> 与模型怎么声明无关。

两个容易误判的地方：

1. **`seed.py` 会静默半成功**：场地、设备两步先 commit 成功，第三步才报错，

   表现是**订单状态已经改了、确认接口却 500、通知丢失**，留下半成品数据。

**模块3 的临时处置**（仅供演示解禁，不是最终方案）：手工插入 id=1 的演示用户，
此后 `seed.py` 与"确认 → 发通知"链路才跑通：

```
id=1  username='demo'  role_id=NULL  status=1
password = $2b$12$80bPxk9SDSvE8HXKZGIpG.jcxpP14PVyQeFOT6Zx.5Aem7r.J96Wa    # bcrypt, cost=12
```

- `role_id` 取 NULL 是**被迫的**：`sys_role` 是空表，填任何值都会撞它自己的外键

- 该哈希由模块3 生成，明文是 `Demo@123456`，**不是认证模块的口径**，属一次性占位

**请认证模块确认三件事**：

1. **谁来灌第一个用户**：迁移不灌数据、公用 backend 无 seed 脚本，初始用户从哪来？

但**公用 backend 全仓不含 `sys_user_role`**（`app/models/system.py` 的 docstring 明确写着
"单角色设计：`sys_user.role_id` 直接外键关联 `sys_role.id`"，云库中该表也不存在）。
已按实际结构修正《技术方案》文档，认证模块请以单角色设计为准。

## 五、公用 backend 的异步引擎会撞 asyncmy 的 `ping` 问题（`pool_pre_ping` 必炸）

**级别**：运行时缺陷。服务一旦跑起来、连接开始复用就必现。

**事实**：`backend/app/core/database.py:38-45` 的异步引擎同时开着 `pool_pre_ping=True`
和 asyncmy 驱动：

```python
async_engine = create_async_engine(
    settings.database_url,      # mysql+asyncmy
    echo=settings.DEBUG,
    pool_size=5, max_overflow=10,
    pool_pre_ping=True,         # ← 触发点
    pool_recycle=3600,
)
```

**实测复现**（直接用公用 backend 自己的 `async_engine` 连云库，同一进程内连续取两次连接）：

```
第1次 connect: OK
第2次 connect: TypeError: AsyncAdapt_asyncmy_connection.ping()
                missing 1 required positional argument: 'reconnect'
```

第一次是**新连接**（不 ping），第二次是**池中复用**（触发 `pool_pre_ping`）。
所以线上表现是**同一接口 200/500 交替**，且只在有流量、连接开始复用之后才出现，
新起服务时完全看不到——非常难查。

**根因**：`MySQLDialect_asyncmy(MySQLDialect_pymysql)` 继承 pymysql 方言的 `do_ping()`，
该方法用 `_send_false_to_ping` 去 introspect **pymysql** 的 `Connection.ping` 签名来二选一
调用形式（`sqlalchemy/dialects/mysql/pymysql.py:78-109`）。当前 PyMySQL 的签名是
`ping(self, reconnect=False)`，判定结果为**无参调用** `dbapi_connection.ping()`；
而真正被调到的是 asyncmy 自己的包装器 `ping(self, reconnect)`——`reconnect`
是**必传**形参（`sqlalchemy/dialects/mysql/asyncmy.py:198`），于是 TypeError。

注意：`_send_false_to_ping` 读的是 **pymysql** 的签名，被调用的却是 **asyncmy** 的包装器，
两者只是名字撞上了。**同步引擎**（`sync_engine`，pymysql 驱动）不受影响。

**建议改法**（模块3 已采用）：给包装器的 `reconnect` 补默认值 `False`，与 SQLAlchemy
想表达的"ping 一下、但不要自动重连"语义一致：

```python
from sqlalchemy.dialects.mysql.asyncmy import AsyncAdapt_asyncmy_connection

if AsyncAdapt_asyncmy_connection.ping.__defaults__ != (False,):
    _upstream_ping = AsyncAdapt_asyncmy_connection.ping

    def _ping(self, reconnect=False):          # reconnect 缺省等价于 False
        return _upstream_ping(self, reconnect)

    AsyncAdapt_asyncmy_connection.ping = _ping  # 子类 AsyncAdaptFallback_… 一并生效
```

比"降级关掉 `pool_pre_ping`"更好：保住了死连接检测，也不动 §3.1 锁定的版本。

**依据**：通读了 `sqlalchemy/dialects/mysql/pymysql.py` 与 `asyncmy.py` 的相关源码；
用公用 backend 自己的 `async_engine` 在云库上复现了上述两次 connect 的对比；
模块3 已加回归用例 `weix/backend/tests/test_asyncmy_ping_compat.py`（6 条，
并已验证"摘掉补丁 / 抽空补丁体"两种情况都会让用例变红）。

## 六、`DATABASE_URL` 一旦指向 SQLite，服务启动即挂（§13.1 应急预案走不通）

`app/core/database.py` 的 `create_async_engine` 无条件传了
`pool_size` / `max_overflow` / `pool_recycle` / `connect_args={"connect_timeout": …}`。
而 `sqlite+aiosqlite` 无论文件库还是 `:memory:` 都会选中 `NullPool`
（`:memory:` 是 `StaticPool`），这两个池的 `__init__` **都不接受**这些参数：

```
TypeError: Invalid argument(s) 'pool_size', 'max_overflow' sent to create_engine(),
using configuration SQLiteDialect_aiosqlite/NullPool/Engine.
```

**触发条件要说准，别记成"团队基线现在就跑不起来"**：

| 场景 | 是否撞上 | 原因 |
| --- | --- | --- |
| 团队现有用例 | **否** | 它们不覆盖 `DATABASE_URL`（仍是 `.env` 里的 MySQL），且自建引擎不含池参数 |
| 模块3 的用例 | 是 | 用例直接用模块级 `async_engine`（`order_service.create_order` 自管会话，§5.5），必须把 `DATABASE_URL` 指向临时 SQLite 才不会写脏云库 —— 覆盖是在 `tests/conftest.py` 顶部加的 |
| **§13.1 的本地镜像库预案** | **是** | 云库断连时按预案把 `DATABASE_URL` 切成 SQLite，**服务会启动即挂，而那时正是最需要它顶上的时候** |

所以这条的严重性不在"测试跑不起来"，而在**应急预案实际不可用**：§13.1 是书面
承诺的兜底手段，而这个参数组合让它从没被执行过。建议集成组在公用基线改成
条件分支（模块3 已在本分支实现，可直接照抄）：

```python
_is_sqlite = settings.database_url.startswith("sqlite")

async_engine = create_async_engine(
    settings.database_url,
    echo=settings.SQL_ECHO,
    pool_pre_ping=True,
    **({} if _is_sqlite else {
        "pool_size": 5,
        "max_overflow": 10,
        "pool_recycle": 3600,
        "connect_args": {"connect_timeout": settings.DB_CONNECT_TIMEOUT},
    }),
)
```

**依据**：`weix/backend/app/core/database.py`（含触发链注释）；
实测三种连接串（文件库 / `:memory:` / 显式 `poolclass=NullPool`）均复现该异常；
另在 9f30d3a 上跑 `pytest --co` 实测团队用例可正常收集（即上表第一行）。

## 七、自定义校验器的中文文案会被通用文案吞掉

`app/core/response.py::_format_validation_error` 里这一行：

```python
message = _VALIDATION_MESSAGES.get(err_type) or err.get("msg") or "参数不合法"
```

Pydantic 对 `field_validator` / `model_validator` 里抛出的 `ValueError` 一律标
`type="value_error"`，而 `_VALIDATION_MESSAGES` 里有 `"value_error": "取值不合法"`。
于是**表命中优先于 `err["msg"]`，校验器里精心写的中文原因被整句替换掉**。

影响面是全体模块，不止本模块：任何用自定义校验器给用户提示的地方都会退化成
"取值不合法"。本模块踩到时，前端拿到的是"参数校验未通过：body 取值不合法"，
而不是"开始时间必须早于结束时间"——用户不知道哪里错了。

两种修法，建议后者：

1. 把 `"value_error"` 从表里删掉 —— 但那会让**没有**自定义 msg 的
   `value_error` 退回到英文原文（Pydantic 的默认 `msg` 是英文），更糟。
2. **自定义校验器产生的 `value_error` 优先用 `err["msg"]`**，其余类型仍走表：

```python
if err_type == "value_error":
    message = err.get("msg") or "取值不合法"
else:
    message = _VALIDATION_MESSAGES.get(err_type) or err.get("msg") or "参数不合法"
```

3. 或者约定各模块不在校验器里写文案、全部下沉到服务层 —— 本模块已按这条做了
   （`schemas/order.py` 的时间校验下沉到 `order_service`，因为 Agent 的
   `lock_resources` Tool 直接调 service、根本不经过模型），但这是**本模块的
   选择，不能替全体模块定**。

**依据**：本模块 `tests/module3/test_orders.py::test_tc02_start_not_before_end`
与 `test_tc03_invalid_time_format` 曾因此变红，现断言里保留了具体文案要求，
防止它复发。
