## 二、🔴 一级冲突：`backend/app/core/database.py`

**这是最危险的一个文件**——同名，但两边几乎是两份不同的实现（团队 68 行 / 本地 109 行）。

### 2.1 两边各自导出什么

| 导出名 | 团队版 | 本地版 |
|---|---|---|
| `Base` | ✅ | ✅ |
| `get_db` | ✅ | ✅ |
| `AsyncSessionLocal` | ✅ | ✅ |
| **异步引擎名** | `async_engine` | **`engine`** |
| **同步引擎** | `sync_engine` + `SyncSessionLocal` | **无** |
| **`PK_TYPE`** | **无** | ✅ |
| **`patch_asyncmy_ping`** | **无** | ✅ |
| 导入方式 | `from app.core.config import settings`（绝对） | `from .config import DATABASE_URL`（相对） |
| `echo=settings.DEBUG` | ✅ 两个引擎都开 | ❌ 未设 |

### 2.2 三个互斥点

**(a) 引擎变量名不同 —— 谁覆盖谁，对面的调用方就断**

- 团队约定 `async_engine`；本模块 `app/main.py:9` 及测试夹具都写的是 `engine`：
  ```python
  from .core.database import Base, engine
  ```
- 反之，若取本地版，团队任何 `from app.core.database import async_engine` 的代码都会 `ImportError`。

**(b) 团队版没有 `PK_TYPE` —— 取团队版会直接崩**

本地三个模型文件第一行就是：

```python
from ..core.database import PK_TYPE, Base
```

`app/models/order.py`、`message.py`、`resource.py` 全部如此。**若把团队版 `database.py` 覆盖进来，
`import app.models` 立刻 `ImportError: cannot import name 'PK_TYPE'`**，服务起不来。

`PK_TYPE` 的作用（本地版注释里写了）：MySQL 下是 `BIGINT`，SQLite 下退化成 `INTEGER`。
因为 **SQLite 只有 `INTEGER PRIMARY KEY` 才是 rowid 别名、才会自增**，裸 `BIGINT PRIMARY KEY`
的 `autoincrement=True` 会被静默忽略。这正是本地 `docs/公用后端问题反馈.md` 的**第一条**问题。

**(c) ping 补丁只在本地 —— 取团队版会让一个已修复的 bug 复现**

团队版 `database.py` 的异步引擎：

```python
async_engine = create_async_engine(
    settings.database_url,
    echo=settings.DEBUG,
    pool_size=5, max_overflow=10,
    pool_pre_ping=True,          # ← 触发点
    pool_recycle=3600,
)
```

**`pool_pre_ping=True` + asyncmy，且没有任何补丁** —— 这正是本地 `docs/公用后端问题反馈.md`
第五节记录的 bug：同一接口 200/500 交替（新连接不 ping，复用连接必炸
`TypeError: AsyncAdapt_asyncmy_connection.ping() missing 1 required positional argument`）。

**本模块已加补丁和回归用例**（`tests/test_asyncmy_ping_compat.py`，6 条）：
今天实测 300 并发请求全 200，无一条报错。**合并时若采用团队版，这个 bug 会原样回来**，
且因为用例跑在 SQLite 上走另一套 `do_ping`，**整套用例仍会全绿，照不出来**。

### 2.3 处理建议（未执行）

推荐**以本地版为基线，补上团队版的两个导出**，而不是反向覆盖：

```python
# 在本地 database.py 末尾追加兼容别名，供团队调用方使用
async_engine = engine            # 团队命名习惯
sync_engine = create_engine(settings.sync_database_url, ...)   # 团队 Alembic/同步脚本需要
SyncSessionLocal = sessionmaker(bind=sync_engine, ...)
```

注意团队 `alembic/env.py` 只用到 `settings.sync_database_url` 和 `Base`，**不直接 import
`sync_engine`**，所以 Alembic 本身不阻塞；但团队若另有同步脚本依赖它，别名能一并兜住。

## 三、🔴 一级冲突：`backend/app/core/config.py`

### 3.1 `extra='forbid'` 导致的成对约束

| | 团队版 | 本地版 |
|---|---|---|
| `env_file` | `".env"`（**相对当前工作目录**） | `BASE_DIR/".env"`（**绝对路径**） |
| `extra` | 未设置 → **pydantic-settings 2.5.2 默认 `'forbid'`**（已实测确认） | `"ignore"` |
| `DATABASE_URL` 字段 | ❌ 未声明 | ✅ 声明（默认 `""`） |
| `AGENT_URL` 字段 | ❌ 未声明 | ✅ 声明 |

**冲突后果（两边必须成对，不能混搭）**：

- **团队版 config + 本模块 `.env`** → 本模块 `.env` 里有 `AGENT_URL=`，
  团队 `Settings` 没声明这个字段，`extra='forbid'` 会**直接抛 `ValidationError`，导入即失败**。
- **本地版 config + 团队 `.env.example` 照抄的 `.env`** → 团队 `.env.example` 里写了
  `DATABASE_URL=mysql+asyncmy://...`，本地版有这个字段所以不报错，**但语义变了**：
  本地版会把 `DATABASE_URL` 当作**优先覆盖**（`database_url` property 里 `if self.DATABASE_URL: return self.DATABASE_URL`），
  于是 `DB_HOST/DB_PORT` 那些配置被**静默忽略**。表现是「改了 `.env` 的端口却不生效」。

**另外**：团队版 `env_file=".env"` 是**相对 CWD** 的。只有在 `backend/` 目录下启动才读得到；
从项目根跑 `uvicorn backend.app.main:app` 会读不到 `.env`，然后拿默认值（空密码）去连库。
本地版用绝对路径规避了这一点。

### 3.2 端口语义不同（同一个 `DB_PORT`，两个意思）

| | 团队 `.env.example` | 本地 `.env` |
|---|---|---|
| `DB_HOST` | `<云服务器IP>` | `127.0.0.1` |
| `DB_PORT` | `3307`（**服务器侧 MySQL 端口**） | `3308`（**本地隧道端口**） |

两边都注释清楚了，但**数值不同、语义也不同**。合并 `.env.example` 时必须保留说明，
否则队友照抄会出现「端口写 3307 但隧道在 3308」的静默连不上。

### 3.3 团队文档提到、但两边都没有的配置

团队 `docs/api.md` 写「超时时间由服务端 `.env` 的 **`AGENT_TIMEOUT`** 配置」。
**团队 `config.py` 和本地 `config.py` 都没有这个字段**。这是一处团队文档与代码不一致，
合并时需与模块 4 负责人（徐川）确认。

## 四、🔴 一级冲突：`backend/app/models/` 表定义重复

### 4.1 同一张表，被两个文件定义

| 表名 | 团队的文件 | 本地的文件 |
|---|---|---|
| `space_resource` | `models/resource.py` | `models/resource.py` ← **同名** |
| `device_resource` | `models/resource.py` | `models/resource.py` ← **同名** |
| `reserve_order` | `models/reservation.py` | `models/order.py` |
| `notify_message` | `models/notification.py` | `models/message.py` |
| `sys_user` / `sys_role` / `sys_permission` | `models/system.py` | 无 |
| `inspect_record` / `repair_ticket` | `models/inspection.py` | 无 |

**风险**：若两套文件同时存在于 `app/models/` 且都被 import，SQLAlchemy 会抛

```
InvalidRequestError: Table 'reserve_order' is already defined for this MetaData instance
```

—— 这是**启动即崩**级别的错误。两者必须只保留一套。

### 4.2 `models/__init__.py` 只能取一个

- 团队版：导入 `system / resource / reservation / inspection / notification`（**绝对导入**）
- 本地版：导入 `message / order / resource`（**相对导入**）

取团队 `__init__.py` 的连带影响：本地 `order.py` / `message.py` 变成孤儿文件（不被导入，无害但冗余）。
取本地 `__init__.py` 的连带影响：**`system.py` / `inspection.py` 不被注册**，
团队 `alembic/env.py` 靠 `from app.models import *` 收集元数据做 autogenerate ——
**这会静默漏掉 3 张 sys_* 表和 2 张巡检表的迁移**。

> 这一条尤其隐蔽：Alembic autogenerate 不会报错，只会少生成表，
> 直到某天有人发现 `sys_user` 没被建出来。

### 4.3 `resource.py` 同名文件的两处实现差异

| | 团队版 | 本地版 |
|---|---|---|
| 主键 | `mapped_column(BigInteger, ...)` | `mapped_column(PK_TYPE, ...)` |
| 索引 | ❌ 无 `Index` 声明 | ✅ 声明了 `idx_*`（注释说明：本模块无 Alembic，`create_all` 是索引唯一来源） |
| 导入 | `from app.core.database import Base` | `from ..core.database import PK_TYPE, Base` |

字段名/类型本身是对齐的（本地 docstring 也写了「与团队公用 `resource.py` 对齐」），
差异只在主键类型、索引声明、导入风格。

> **2026-09-26 实测更正**：上表「本地声明了 `idx_*`」**不代表云库里有这些索引**。
> 直查云库 `smart_scheduler_dev` 的 `information_schema.STATISTICS`，`idx_*` **一个都不存在**
> —— 本地那套 `Index` 声明是这些索引唯一存在过的地方。详见 11.1。

### 4.4 `reserve_order.user_id` 的引用方式不同

- **团队**：真外键 `ForeignKey("sys_user.id")`
- **本地**：**软引用**，无外键。本地注释说明了原因——本模块要保持自包含，
  不引入 `SysUser` 实体，否则 `create_all` 解析 `sys_user` 时抛 `NoReferencedTableError`。

合并时待确认：**云库到底有没有这个外键**。

> **2026-09-26 实测更正 —— 有，且团队版才是与云库一致的一方。**
> 云库 `information_schema.STATISTICS` 里 `reserve_order.user_id`、`notify_message.receiver_id`
> 上都有索引（MySQL 为外键自动生成），即真外键确实存在。**本地的「软引用」版本会低估写路径
> 的约束**：插入不存在的 `user_id` 在云库上会被 1452 挡住。故本次对齐采纳团队的真外键，
> 连带影响见 `tests/module3/conftest.py` 新增的 `_seed_users()` —— 写 `reserve_order` 前
> 得先有 `sys_user` 行。这条与 `docs/公用后端问题反馈.md` 第四条是同一件事的两面。

## 五、🟠 二级冲突

### 5.1 `backend/app/schemas/agent.py` —— Agent 契约已被冻结

**这是业务影响最大的一条。** 团队 `docs/api.md` 里模块 4 明确标注：

> 负责人：徐川 ｜ 状态：**契约已冻结（阶段 2）**
> `trace` 元素结构（前端按此逐字段渲染，**字段不可中途变更**）

| 项 | 团队冻结契约 | 本模块实现 |
|---|---|---|
| 请求模型名 | `ScheduleRequest` | `AgentScheduleRequest` |
| 响应模型 | `Plan` / `TraceStep` / `ScheduleData` | **未定义**（`agent_client` 直接返回裸 dict） |
| `trace` 元素 | **对象数组**：`step` / `result` / `timestamp` / `thought` / `action` / `actionInput` / `observation` | **字符串数组** |
| `plan.spaceName` | ✅ 文档要求有 | ❌ 本地 mock 返回的是 `title`，**没有 `spaceName`** |
| `timestamp` | 「各步互不相同且递增」，前端做时间轴回放 | 字符串数组**无从满足** |
| 认证 | `Authorization: Bearer <JWT>` | `X-User-Id: 1`（演示占位） |

**本地实际返回**（今天实测 `POST /api/v1/agent/schedule`）：

```json
{"plan": {"spaceId": 1, "deviceIds": [1], "startTime": "...", "endTime": "...",
          "title": "主方案 · 会议室A", "reason": "场地空闲，满足需求"},
 "backupPlan": {...},
 "trace": ["解析需求：...", "查询可用场地与设备资源", "检测时段冲突，进行方案权衡", "生成主方案与备方案"],
 "needConfirm": true}
```

对照团队契约，`trace` 是**字符串数组**、`plan` 用 `title` 而非 `spaceName` ——
**前端（模块 8 / 模块 9）按 `TraceStep` 逐字段渲染时会拿到 undefined**。

本地 `docs/api.md:160` 也是按字符串数组记录的，即**本地文档与实现自洽，但两者都偏离了团队冻结契约**。

**注意本模块的定位**：本地 `app/agent/__init__.py` 写明「核心调度 Agent 由 AI 决策核心组负责，
本模块不直连 LangChain，统一通过 `services/agent_client.py` 以 HTTP 调用 Agent 接口；
`AGENT_URL` 为空时走内置 mock 调度器」。

所以这**不是谁写错了**，而是**mock 的契约没有对齐模块 4 的冻结契约**。
`AGENT_URL` 配好、连上模块 4 真实接口后，真实 `trace` 自然是对象数组，
本模块的 mock 需要跟着改（否则 mock 演示与真实接口表现不一致，前端联调会被误导）。

**好消息**：团队契约里的两条禁令本模块已符合——
「不存在 `/api/v1/tools/*` 路由」、「请求体不接受 `userId`」。

### 6.1 ⚠️ 云库当前种子数据 ≠ 团队权威 `docs/seed.sql`，已导致评审场景失效

团队 `docs/seed.sql` 是**权威种子数据**，明确写了数值被五个评审场景的断言反向约束，

### 10.2 ⚠️ 两处需要集成组签字的语义决定

这两条**不是**本模块单方面能定的，改了会影响模块 2 的既有测试，请集成组裁决。

**（1）参数校验失败走 HTTP 422，而不是 HTTP 200 + `body.code=400`**

两套实现原本互斥：模块 2 主张「所有响应 HTTP 恒为 200」，本模块主张「校验/不存在/冲突走真实状态码」。
规范 §5.2 只规定响应体结构 `{code, message, data}`，**对 HTTP 状态码未作规定**，故无法从规范直接裁决。

最终依据**团队共享的 `docs/api.md`**（第 14–15、138–142 行）：
> 「**降级路径同样返回 HTTP 200 且保持本结构**，不抛 500」
> | 200 | 200 | 正常，或上述任一降级路径 |
> | —   | 422 | `text` 为空或超长 |

即 HTTP 200 只留给「正常」与「降级」两类。据此确定的各处理器口径：

| 异常类型 | HTTP | body.code | 依据 |
|---|---|---|---|
| `BusinessError` | **200** | 业务码（如 41001） | `exc.code` 不是合法 HTTP 状态，只能放 body；正对应「降级路径返回 200」 |
| `RequestValidationError` | **422** | 422 | 团队 `docs/api.md` 的 422 行 |
| `StarletteHTTPException` | 原样透传 | 同 HTTP | 路由显式指定 404/409 |
| `IllegalTransitionError` | 409 | 409 | 状态机非法流转兜底 |
| 未捕获异常 | 500 | 500 | 只回「服务器内部错误」，堆栈仅进日志（§9.2） |

注意 `BusinessError` 与其余四条**并不矛盾**：它承载「业务降级」，正是 docs/api.md 所说
「降级路径返回 HTTP 200」。两者是分工。

**受影响用例**：`tests/test_image_api.py::test_missing_file_returns_friendly_error`
断言缺 `file` 字段时 HTTP 200 + `body.code=400`，现为 422。**请集成组确认以 422 为准**，
或改回 200 + 400 —— 但那样与本模块 404/409 的口径不一致，前端要写两套解析。

> **2026-09-28 后续：本条已由 main 自行定案，不需要集成组再裁决。**
> 新 main 在 `core/exceptions.py` 里定义了 `ParamInvalidError`
> （`code = ErrorCode.PARAM_INVALID` 即 40001、`http_status = 400`），即 Pydantic 校验
> 失败取「**HTTP 400 + 业务码 40001**」这条 —— 既不是当初的 422，也不是 200 + 400。
> 本模块已按 400 对齐（见 PR 文档 §3.1），断言与实现同步改过。

**（2）`Settings.extra` 由 `"forbid"` 改为 `"ignore"`**

pydantic-settings 默认 `extra="forbid"`：`.env` 里出现任何未声明字段都会让应用**启动即失败**。
这在本项目不成立 —— 两边 `.env.example` 都列了 `config.py` 未声明的键，（见 §3.3），
合并后必然启动不了。改为 `"ignore"`。

**代价（必须知道）**：拼错的键名会被**静默忽略**，写了不生效且毫无提示。
另外注意本模块与团队 `.env.example` 里的所有说明性注释文字，都不会被当作键读取。
