## 1. 三个必须先讲清的发现

### ① `get_db` 语义**本来就对齐**（我先怀疑是个坑，核实后不是）

新 main 的 `get_db` 刻意**不提交**（§5.5 要求业务层显式 commit），docstring 里写死了这条。
我们那版**也不提交** —— 我们的 `orders.py` 里本来就有显式提交：

```
app/api/orders.py:84, 153, 186   await db.commit()
app/api/messages.py:75, 89       await db.commit()
```

两边只差一行：我们多写了个 `finally: await session.close()`（与 `async with` 重复）。
**取 HEAD 即可，模块 3 无需改动。**

### ② 集成组的错误码表**已经为订单/预约预留了码位**

```
40402 SPACE_NOT_FOUND        40404 ORDER_NOT_FOUND
40403 DEVICE_NOT_FOUND       40901 RESOURCE_CONFLICT
                             40903 ORDER_STATUS_CONFLICT
```

集成组在 §3 冲突 2 已裁决：**「以本地的真实 HTTP 状态码 + 5 位业务码为准」** ——
方向是模块 3 的（HTTP 状态码真实、语义码留在 `body.code`），
但**码值要迁到他们表里这 5 位码**，不能沿用模块 3 自造的那几个。
这不是冲突解决，是**要改代码**。

### ③ 「只读桩」定位到了

你说的 `orderId` 恒 `None`，源头是 `app/api/v1/mock.py` 里的常量 `"orderId": 1001`。
新 main 确实没有真实的 `create_order`。

## 3. 待你拍板的三点

### A. 模型要不要声明 §6.6 索引？（与既有结论相反，情况变了）

我此前记录过：*云库缺 §6.6 全部索引、模型跟团队不声明索引、别照 spec 补回去*。
**现在这条过期了** —— 集成组这轮自己补上了，而且是两处同时补：

```
app/models/*.py           __table_args__ 里声明 Index(...)
alembic/versions/b7f1c4a92e35_add_doc66_indexes_idempotent.py
```

取舍：取 HEAD 意味着跟随团队声明索引。
**但我没验证过那个迁移在云库上跑了没有** —— 如果没跑，声明了索引也不会真的建出来
（声明只是 metadata，真正建表/建索引靠迁移）。
建议：取 HEAD，然后单独确认 `b7f1c4a92e35` 的云端执行状态。

### B. `PK_TYPE` 能不能丢？（关系到 SQLite 用例死活）

新 main 的模型用裸 `BigInteger`。SQLite 下 `BIGINT PRIMARY KEY` **不是** rowid 别名、
不会自增，而模块 3 的用例跑在临时 SQLite 上。
但新 main 的 `conftest.py` **换了套做法**（`db_path(tmp_path)` 每用例一个文件库＋
自己的 `_make_engine` 工厂），可能已经用别的方式绕过了。

`PK_TYPE` 对 MySQL 是**无损**的（渲染出的 DDL 与 `BigInteger` 完全一致，仍是 BIGINT），
所以保留它零风险。
建议：先保留，等在新基线上真跑一遍模块 3 用例，红了再决定去留。

### C. 业务码迁移的范围

模块 3 现在用自造的 4 位码（如 `_fail("not_found", ...)`），
要逐调用点换成 `ErrorCode.ORDER_NOT_FOUND` 这类 5 位码。
这是**改动量最大的一块**，且会连带改断言（用例里现在写的是 4 位码）。
建议：单独作为一个提交做，别混在冲突解决里 —— 否则出了问题分不清是合并错还是迁移错。
