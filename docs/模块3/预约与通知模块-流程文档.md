# 移动端预约与通知模块 —— 流程文档（细粒度）

> 依据《新建文本文档.txt》实现计划整理。本文档描述模块内每一条业务流程在「用户 → 小程序端 → FastAPI 后端 → 数据库/Agent/WebSocket」之间的完整流转，粒度细化到**单次 API 调用、单次状态变迁、单次数据落库、每个异常分支**。
>
> 适用对象：开发自测、联调对齐、验收演示。
> 配套资料：目录结构、接口清单、状态机定义均以《新建文本文档.txt》为准，本文档不重复罗列，只展开"流程"。

---

## 1. 文档说明

### 1.1 目的
明确模块内各业务场景的**端到端执行顺序**、**每一步的触发方与执行方**、**关键数据/状态的变化**，以及**异常与边界情况下的处理路径**，作为实现与验收的依据。

### 1.2 术语表

| 术语 | 含义 |
|---|---|
| 小程序端 | Uni-app（Vue3 组合式 API）微信小程序 |
| 后端 | FastAPI + SQLAlchemy，默认 SQLite，可切 MySQL |
| 状态机 | 预约状态流转的唯一裁决入口（`state_machine.py`） |
| 通知 | `notify_message` 表中的一条记录，配合 WebSocket 实时推送 |
| 订阅消息 | 微信小程序 `requestSubscribeMessage` 授权后，服务端下发的模板消息（本项目封装占位） |
| Agent | 调度 Agent（队友模块），本模块通过 `agent_client` 单一入口集成，未接入时走 mock |
| mock 用户 | 演示阶段固定 `user_id = 1`，通过 `X-User-Id` 请求头解析 |

### 1.3 关键约定（影响流程理解）

- **状态机是唯一写入通道**：任何 `reserve_order.status` 的变更必须经过 `state_machine.transition()`，直接改库视为非法。
- **通知与业务解耦**：业务动作（确认/取消）成功后，通过 `notify_service.create_and_push()` 异步式地"落库 + 推送"，通知失败不影响业务主流程。
- **Agent 走单一入口**：本模块不直连 LangChain，一律调 `agent_client`；`AGENT_URL` 未配置或调用失败时自动降级 mock，保证可独立演示。
- **双端身份**：后端用 `X-User-Id` 头模拟用户，预留 JWT 对接点；前端在 `request.js` 统一注入。

## 2. 系统角色与边界

| 角色 | 职责 | 在流程中的位置 |
|---|---|---|
| 用户（蔡玉礼） | 触发操作、授权订阅消息、查看结果 | 发起方 |
| 小程序端 | 表单交互、接口调用、WebSocket 建连、订阅消息授权、状态展示 | 中间层 |
| FastAPI 后端 | 校验、状态机裁决、落库、通知生成与推送、Agent 调用 | 核心裁决层 |
| 状态机 | 校验状态流转合法性，执行流转副作用 | 后端内部 |
| notify_service | 生成通知文案、写表、触发 WebSocket 推送 | 后端内部 |
| ConnectionManager（websocket.py） | 维护用户连接、定向推送 | 后端内部 |
| agent_client | 调用 Agent 或降级 mock，返回结构化方案 | 后端内部 |
| 数据库（SQLite/MySQL） | 持久化 4 张表 | 存储层 |
| 调度 Agent（队友模块） | 解析需求、生成预约方案、多模态识别（接入后） | 外部依赖 |

## 3. 总体流程概览

模块完整业务闭环分三条主线，彼此通过"状态机 + 通知"串联：

```
主线 A（预约生命周期）
  资源获取 → 创建预约(PENDING) → 确认(CONFIRMED) → 完成(COMPLETED)
                                          └── 取消(CANCELLED)

主线 B（通知闭环）
  业务动作成功 → notify_service 落库 + WebSocket 推送 → 前端更新未读角标 → 订阅消息提醒

主线 C（Agent 联动）
  文本/语音/图像入口 → agent_client 调度 → 展示思考过程 → 确认方案 → 复用主线 A 创建预约
```

### 4.1 用户身份识别流程（贯穿所有接口）

**触发**：小程序端发起任意需鉴权接口请求。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 小程序端 | `utils/request.js` 在请求头注入 `X-User-Id: 1`（演示写死；预留从登录态读取） | 请求头携带身份 | 无 |
| 2 | 后端 `deps.py` | 从请求头解析 `X-User-Id`，返回当前用户对象 | 得到 `user_id=1` | 头缺失 → 返回 401/默认 mock 用户，提示"未携带用户身份" |
| 3 | 后端路由 | 用 `Depends(get_current_user)` 获取用户，后续写表/推送均以该 `user_id` 为准 | 锁定目标用户 | 无 |

**说明**：JWT 双 Token 对接点在此预留；真实登录接入后仅需改 `deps.py`，上层流程不变。

### 4.3 预约创建流程（Part 1 核心）

**触发**：用户在 `reserve/create.vue` 填写表单并点击"提交预约"。

**前置条件**：已选场地/设备/日期/时段/人数，前端校验已通过。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 小程序端 | 前端校验：日期/时段非空、`start < end`、人数 > 0、场地设备已选 | 前端校验态 | 校验失败 → 就地红字提示，不发起请求 |
| 2 | 小程序端 | `api/reserve.js` 调 `POST /api/reservations`，body 含场地/设备/时段/人数 | 发起创建请求 | 网络失败 → 统一错误提示 |
| 3 | 后端 `schemas.py` | Pydantic 强校验：`start < end`、人数 > 0、场地/设备存在性 | 请求体校验 | 校验失败 → 返回 422 及字段级错误 |
| 4 | 后端 `reservations.py` | 冲突检测：查询该场地/设备在时段内是否已有 `CONFIRMED/PENDING` 订单（硬编码兜底） | 冲突判断 | 冲突 → 返回 409"时段已被占用"，前端提示 |
| 5 | 后端 `state_machine.py` | 创建订单并置初始状态 `PENDING`（通过状态机写入，保证合法） | 新增 `reserve_order` 一行，`status=PENDING` | 状态机拒绝 → 返回 400 |
| 6 | 后端 | 返回创建结果（含 `id`、`status`、完整字段） | 201 响应 | 落库失败 → 500，回滚 |
| 7 | 小程序端 | 提示"预约已提交，待确认"；跳转 `detail.vue` 或返回列表 | 页面跳转 | 无 |

**产出**：`reserve_order` 新增一条 `PENDING` 记录。

---

### 4.4 预约确认流程

**触发**：用户在 `detail.vue` 点击"确认预约"。

**前置条件**：订单当前状态为 `PENDING`。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 小程序端 | 调 `POST /api/reservations/{id}/confirm` | 发起确认请求 | 无 |
| 2 | 后端 | 查询订单，校验存在且 `status == PENDING` | 订单读取 | 不存在 → 404；状态不符 → 409 |
| 3 | 后端 `state_machine.py` | 校验 `PENDING → CONFIRMED` 合法，执行流转 | `status = CONFIRMED` 落库 | 非法流转 → 400"非法状态流转" |
| 4 | 后端 `notify_service.py` | 生成 `RESERVATION_CONFIRM` 类型通知：写 `notify_message` 表 | 新增通知记录（`user_id=1`、未读） | 通知落库失败 → 记录日志，不影响订单 |
| 5 | 后端 `websocket.py` | 通过 `ConnectionManager` 向目标用户定向推送通知 | 实时消息到达前端 | 用户未在线 → 跳过推送，通知仍可查列表 |
| 6 | 小程序端 | `ws.js` 收到推送 → 更新 Pinia 未读数 | 未读角标 +1 | 断连 → 靠心跳重连后补拉 |
| 7 | 小程序端 | 触发 `requestSubscribeMessage` 封装，引导订阅消息授权 | 授权态 | 用户拒绝 → 静默跳过，不阻塞 |

**产出**：订单 `CONFIRMED`；新增一条确认通知；前端未读角标 +1。

---

### 4.5 预约取消流程

**触发**：用户在 `detail.vue` 或 `list.vue` 点击"取消预约"。

**前置条件**：订单状态为 `PENDING` 或 `CONFIRMED`（取消态下不可再取消）。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 小程序端 | 二次确认弹窗（`uni.showModal`） | 确认交互 | 用户点取消 → 流程终止 |
| 2 | 小程序端 | 调 `POST /api/reservations/{id}/cancel` | 发起取消请求 | 无 |
| 3 | 后端 | 查询订单，校验状态为 `PENDING` 或 `CONFIRMED` | 订单读取 | 不存在 → 404；已是 `CANCELLED/COMPLETED` → 409 |
| 4 | 后端 `state_machine.py` | 校验 `PENDING/CONFIRMED → CANCELLED` 合法，执行流转 | `status = CANCELLED` 落库 | 非法 → 400 |
| 5 | 后端 `state_machine.py` | **若原状态为 `CONFIRMED`**：触发"释放场地/设备占用"副作用 hook | 释放占用（预留 hook） | hook 异常 → 记录日志，不中断主流程 |
| 6 | 后端 `notify_service.py` | 生成 `DELAY_APOLOGY` 或取消相关通知，落库 + 推送 | 新增通知记录 | 失败不阻塞 |
| 7 | 小程序端 | 收到推送 → 更新未读 + 刷新列表状态为"已取消" | 列表状态更新 | 无 |

**产出**：订单 `CANCELLED`；若原为 `CONFIRMED` 则释放占用；生成取消通知。

### 4.6 预约状态机流转汇总（含非法拦截）

状态枚举：`PENDING / CONFIRMED / COMPLETED / CANCELLED`。

```
PENDING(待确认) ──确认──▶ CONFIRMED(已确认) ──完成──▶ COMPLETED(已完成)
     │                        │
     └─────取消──▶ CANCELLED ◀─────取消──────┘
```

合法流转表（`TRANSITIONS`）：

| 当前状态 | 目标状态 | 是否合法 | 触发接口 | 副作用 |
|---|---|---|---|---|
| PENDING | CONFIRMED | ✅ | `/confirm` | 无 |
| PENDING | CANCELLED | ✅ | `/cancel` | 无 |
| CONFIRMED | COMPLETED | ✅ | 完成接口/定时 | 无 |
| CONFIRMED | CANCELLED | ✅ | `/cancel` | 释放占用 hook |
| COMPLETED | 任意 | ❌ | — | 终态 |
| CANCELLED | 任意 | ❌ | — | 终态 |
| PENDING/CONFIRMED → 其它未列项 | — | ❌ | — | 直接拒绝 |

**非法流转处理**：`can_transition(from, to)` 返回 False → 后端返回 400，前端提示"当前状态不允许该操作"，数据库不变。

### 4.7 通知生成与推送流程（`notify_service.create_and_push`）

**触发**：任一业务动作成功后调用（确认、取消、提醒、冲突）。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 业务路由 | 调用 `create_and_push(user_id, type, payload)` | 入参：接收人、类型、业务载荷 | 无 |
| 2 | `notify_service` | 按 `type` 生成通知文案（`RESERVATION_CONFIRM / SCHEDULE_REMIND / CONFLICT_ALERT / DELAY_APOLOGY`） | 组装文案 | 类型未知 → 使用默认文案 |
| 3 | `notify_service` | 写 `notify_message` 表（`user_id`、`type`、`content`、`is_read=0`、时间） | 新增通知记录 | 写库失败 → 记录日志并返回，**不抛出**影响业务 |
| 4 | `notify_service` | 调 `ConnectionManager.send_to_user(user_id, message)` | 定向推送 | 用户不在线 → 静默跳过 |
| 5 | `websocket.py` | 遍历该用户所有活跃连接，`send_json` | 消息实时送达 | 单连接发送失败 → 移除该连接，继续 |
| 6 | 小程序端 `ws.js` | 收到消息 → 分发到 Pinia store | 未读数 +1、通知列表头部插入 | 无 |

**要点**：通知是"尽力而为"（best-effort），落库与推送分离，**推送失败不影响落库**，用户可通过列表接口补看。

### 4.8 订阅消息授权流程（`requestSubscribeMessage`）

**触发**：前端收到实时通知后，或用户在通知页主动开启提醒。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |

| 1 | 小程序端 | 调 `uni.requestSubscribeMessage`（封装），声明所需模板 ID | 弹出微信授权弹窗 | 无模板 ID → 跳过 |
| 2 | 微信 | 用户选择"允许/拒绝" | 授权结果返回 | — |
| 3 | 小程序端 | 记录授权结果 | 本地授权态 | 用户拒绝 → 静默，不阻塞业务 |
| 4 | 小程序端 | 将授权结果回传后端（预留，真实订阅消息由服务端下发） | 预留接口 | 未实现 → 仅前端占位 |

**说明**：本项目订阅消息为"封装 + 占位"，真实服务端下发由后续接入。

### 4.9 通知读取流程（列表 / 未读数 / 已读 / 全读）

**触发**：用户进入 `notify/list.vue` 或查看未读角标。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 小程序端 | `onShow` 调 `GET /api/notifications`（分页）+ `GET /api/notifications/unread-count` | 发起请求 | 网络失败 → 统一提示 |
| 2 | 后端 | 返回当前用户通知列表（分页）+ 未读总数 | 响应 JSON | 无 |
| 3 | 小程序端 | 渲染列表，未读项高亮；更新 Pinia 未读数 | 界面刷新 | 无 |
| 4 | 用户 | 点击某条通知 → 调 `POST /api/notifications/{id}/read` | 单条已读 | 无 |
| 5 | 后端 | 将该条 `is_read` 置 1 | 数据更新 | 不存在 → 404 |
| 6 | 小程序端 | 前端将该条置为已读态，未读数 -1 | 局部刷新 | 无 |
| 7 | 用户 | 点击"全部已读" → 调 `POST /api/notifications/read-all` | 批量已读 | 无 |
| 8 | 后端 | 将该用户所有通知 `is_read` 置 1 | 数据更新 | 无 |
| 9 | 小程序端 | 清空未读角标，列表全部置已读态 | 界面刷新 | 无 |

### 4.10 Agent 文本联动流程（Part 3 核心）

**触发**：用户在 `agent/schedule.vue` 文本输入框输入需求（如"帮我预约明天下午的会议室"）并提交。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 小程序端 | 调 `api/agent.js` → `POST /api/agent/schedule`，body 含 `requirement` 文本 | 发起调度请求 | 空文本 → 前端拦截 |
| 2 | 后端 `agent.py` | 接收需求，调 `agent_client.schedule(requirement, trace)` | 进入调度 | 无 |
| 3 | `agent_client` | 判断 `AGENT_URL` 是否配置、是否可用 | 选择真实/mock | 未配置或失败 → 降级 mock（步骤 4） |
| 4a | `agent_client`(真实) | POST 到 `AGENT_URL`，返回结构化方案 | 得到方案 JSON | 超时/异常 → 降级 mock |
| 4b | `agent_client`(mock) | 本地 mock 调度器：生成主/备方案 + 伪思考步骤 | 得到 mock 方案 | 无 |
| 5 | 后端 `agent.py` | 返回方案（含候选时段、资源、冲突提示、`agent_trace` 思考步骤） | 响应 JSON | 无 |
| 6 | 小程序端 | 轮询/展示 `agent_trace`，逐步渲染「解析→查询→冲突→权衡→方案」 | 思考过程动画 | 轮询中断 → 提示重试 |
| 7 | 小程序端 | 渲染主/备方案卡片，供用户选择 | 方案展示 | 无 |

**产出**：前端拿到结构化方案 + 思考过程，等待用户确认。

| 4 | 小程序端 | 识别结果作为需求上下文，走 4.10 调度流程 | 复用调度流程 | 无 |

### 4.13 Agent 方案确认落库流程

**触发**：用户在方案卡片点击"确认此方案"。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 小程序端 | 调 `POST /api/agent/confirm`，body 含选中的方案 ID/内容 | 发起确认 | 无 |
| 2 | 后端 `agent.py` | 校验方案有效，转为预约创建请求；**持久化 `agent_request`（原始需求）+ `agent_trace`（思考日志 JSON）** | 方案 → 预约（含 AI 溯源字段） | 方案失效 → 400 |
| 3 | 后端 | 复用 4.3 创建流程（含校验、冲突检测、状态机 `PENDING`） | 新增 `reserve_order`（含 `agent_request`/`agent_trace`） | 冲突 → 409 提示重选 |
| 4 | 小程序端 | 跳转预约列表，新单出现（`PENDING`） | 页面跳转 | 无 |
| 5 | 后端 | 若触发通知，走 4.7 推送 | 通知 + 未读角标 | 无 |

**要点**：Agent 确认落库与手动创建**复用同一套状态机与校验**，保证数据一致性。

---

### 4.14 WebSocket 连接管理流程（`ws.js` + `websocket.py`）

**触发**：小程序端登录/启动后建立长连接。

| 步骤 | 执行方 | 动作 | 数据/状态变化 | 异常分支 |
|---|---|---|---|---|
| 1 | 小程序端 | `ws.js` 连接 `/ws/notify?user_id=1` | 建连 | 连接失败 → 指数退避重连 |
| 2 | 后端 `websocket.py` | `ConnectionManager` 注册该用户连接 | 连接表 +1 | 无 |
| 3 | 小程序端 | 启动心跳（定时 ping） | 保活 | 无 |
| 4 | 后端 | 收到心跳，确认存活 | 连接保活 | 超时未心跳 → 判定断开，清理连接 |
| 5 | 小程序端 | 断线后自动重连，成功后补拉通知列表 | 重连 | 多次失败 → 停止并提示 |
| 6 | 小程序端 | 收到服务端消息 → 分发：更新未读 + 触发订阅消息 | 未读 +1 | 无 |

**要点**：断线重连、心跳、消息分发三项由 `ws.js` 统一封装。

## 5. 数据流转与表状态变化汇总

### 5.1 表与状态字段

| 表 | 关键字段 | 状态变化触发点 |
|---|---|---|
| `space_resource` | 名称/位置/容量/预算/开放时间/绑定设备 id 集合 | 仅造数读取，不流转 |
| `device_resource` | 名称/类型/归属场地/状态 | 仅造数读取，不流转 |
| `reserve_order` | `status`(PENDING/CONFIRMED/COMPLETED/CANCELLED)、`device_ids`、`agent_request`、`agent_trace` | 4.3/4.4/4.5/4.13 由状态机写入；Agent 创建时落 `agent_request`/`agent_trace` |
| `notify_message` | `is_read`(0/1)、`type`、`content` | 4.7 落库，4.9 置已读 |

### 5.2 一次完整闭环的数据快照

以"创建 → 确认 → 取消"为例：

| 时间点 | `reserve_order.status` | `notify_message` 新增 | 前端未读角标 |
|---|---|---|---|
| 创建后 | PENDING | — | 0 |
| 确认后 | CONFIRMED | RESERVATION_CONFIRM 一条 | +1 |
| 取消后 | CANCELLED | DELAY_APOLOGY 一条 | +1 |

## 6. 异常与边界场景汇总

| 场景 | 触发条件 | 处理 | 用户可见结果 |
|---|---|---|---|
| 时段冲突 | 创建时该资源已被占用 | 后端 409 | 提示"时段已被占用" |
| 非法状态流转 | 对终态/错误状态执行 confirm/cancel | 状态机 400 | 提示"当前状态不允许该操作" |
| 表单校验失败 | 时间颠倒/人数≤0/未选资源 | 前端拦截 + 后端 422 | 就地字段级提示 |
| 通知推送时用户离线 | 用户未连 WebSocket | 跳过推送，落库保留 | 列表接口可补看 |
| Agent 服务不可用 | `AGENT_URL` 未配置/超时 | `agent_client` 降级 mock | 正常返回 mock 方案 |
| ASR/图像未接入 | 队友模块未交付 | 占位回显 | 回显占位文本 |
| WebSocket 断线 | 网络抖动 | 心跳检测 + 重连 + 补拉 | 恢复后未读不丢 |
| 用户拒绝订阅消息 | 授权弹窗点拒绝 | 静默跳过 | 不影响业务，仅少提醒 |
| 取消 CONFIRMED 订单 | 需释放占用 | 触发释放 hook | 资源占用解除 |
| 未携带 `X-User-Id` | 请求头缺失 | `deps.py` 兜底 mock 用户/401 | 提示身份缺失 |
