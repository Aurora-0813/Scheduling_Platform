## P1 · 状态机 `2已确认 → 4已完成` 无入口

**事实**

- `app/state_machine.py:24` 声明了合法流转 `CONFIRMED -> {COMPLETED, CANCELLED}`。
- 但 `OrderStatus.COMPLETED` 在全仓库**只出现于 `state_machine.py` 自身**（第 18、24、25 行）。
  没有任何路由、服务或定时任务会产生状态 4。
- 模块3 实际提供的状态变更入口只有两个：`PUT /orders/{orderId}/confirm`（`app/api/orders.py:176`，
  1→2）与 `PUT /orders/{orderId}/cancel`（`app/api/orders.py:206`，1→3 / 2→3）。

**为什么是问题**

1. `§6.3` 把 `order_status` 的取值域定为 1/2/3/4，`§5.3` 的验收里也有「已完成」这一档。
   状态 4 不可达 ⇒ 这一档**永远验收不到**。
2. 订单确认后**永远不会离开状态 2**。而「占用资源」的口径是 `ACTIVE_ORDER_STATUSES = (1, 2)`
   （`app/models/reservation.py:34`），意味着**历史上所有确认过的订单都永久算作占用**。
3. 对「时段冲突」判定目前**尚无影响** —— `order_service._time_conflicts` 除了状态还带了时间
   窗口谓词（`end_time > start AND start_time < end`），过期的单不会与新单重叠，所以不会
   误报冲突。但**任何按状态计数的口径都会偏高**（例如模块 8 看板若按 `status IN (1,2)`
   统计在占用资源数）。
4. 与 P2 耦合：如果设计意图是「完成时才释放占用 / 回补库存」，那么 P1 不解决，P2 的
   `available_count` 回补路径就**永远不会被走到**。

**需要定的是**

- **谁**把订单推进到 4？候选：(a) 定时任务扫描 `end_time < now` 的已确认单；
  (b) 用户/管理员手动点「已完成」；(c) 由核心调度 Agent 在会话结束时收尾。
- 如果取 (a)：调度入口由谁提供、用什么密钥保护（与 **P4 是同一个口子**，建议合并决策）。
- 如果取 (b)：需要在模块3 增加一个 `POST /orders/{orderId}/complete`，属**新增契约**，
  需要确认接口路径与是否进 `§5.3` 清单。

**模块3 的建议**：取 (a) + 一个受密钥保护的内部入口。理由：预约的「完成」是**时间驱动**的
客观事实（时间过了就是过了），不该依赖用户点按钮；演示时也更容易讲清。若同时采纳，
`ACTIVE_ORDER_STATUSES` 可以保持不变（它表达的是列的语义），由定时任务负责把过期的单移出 1/2。

**需要什么答复**：取哪个方案；若取 (a)，调度入口与密钥归谁（与 P4 一并答复）。

## P2 · `release_occupancy` 是空实现，`available_count` 只读不写

> **2026-09-28 更新：本条已结。** 口径取「用时推导」（下表的 (b')），已实现；
> `release_occupancy` 已**删除**（函数 + 调用点 + monkeypatch 用例）。起因是模块 4 的
> AGENT-C-01/02 需要可验证的口径，而 `§5.3` / `§6.3` 都没写。完整判据、代价与
> AGENT-C-01/02 的 7 条对照表见 `docs/available_count口径判据.md`。
> 下面保留的是决策当时的记录。

**事实**

- `app/state_machine.py:46-52`：`release_occupancy(order)` 函数体是 `pass`，注释为
  「预留 hook……真实占用管理接入后在此实现」。它被 `app/api/orders.py` 在取消「已确认」
  订单时调用 —— **调了，但什么也没发生**。
- `available_count`：`order_service._check_devices` 只做 `available_count > 0` 的**校验**，
  全模块**没有任何扣减**，取消路径也**没有回补**。
- `§5.5` 的事务六步里既没有扣减、也没有回补。

**为什么是问题**

- 单方面扣减会造出**第二份真值**：场地的占用已经可以从 `reserve_order` 按状态 + 时间窗口
  派生出来，再用一个计数器维护同一件事，两者一旦不一致就无法判断谁对。
- 不扣减则「库存」这个概念形同虚设 —— 演示 AGENT-C-02（并发与库存扣减）时，
  没有可观测的扣减效果，用例只能验证「没超卖」而验证不了「扣了」。
- `release_occupancy` 半死不活比没有更糟：调用点看起来在做释放，实际是空操作，
  读代码的人容易据此以为占用管理已经实现。

**`available_count` 到底是存储字段还是派生值**

| 方案 | 含义 | 代价 |
| --- | --- | --- |
| (a) 存储字段 | 创建时扣、取消/完成时回补，`FOR UPDATE` 下原子更新 | 需要与 `reserve_order` 保持一致的补偿逻辑；异常路径漏回补就会永久少库存（**完成**那条尤其容易漏，见判据文档 §2） |
| (b) 派生值 | `available_count := total_count − 当前占用数`（按 P1 的口径算） | 需要 `§6.6` 的索引支持；读写都变成聚合查询 |
| (c) 只读不写 | 维持现状，字段仅作「该类设备是否可借」的布尔门 | 必须**明确写进文档**，并删掉 `release_occupancy` 调用，避免继续误导 |
| **(b') 用时推导（已实现）** | 取 (b) 的派生思路但**不改字段语义**：`available_count` 是**可用上限**（管理员维护、静态），剩余量 = `available_count − 该时段重叠单数`，每次创建**算**一遍 | 与 (b) 同样需要设备维度索引；`§6.6` 的 10 个 `idx_*` 里没有，这一步只能全表捞活跃重叠单再在 Python 里数（已标注「不做性能承诺」） |

选 (b') 而不是 (b)：`device_resource` 上 `total_count` 与 `available_count` 两列并存，
说明二者不同义（后者是留出备用机后的**上限**）。(b) 让 `available_count` 不再是管理员
能直接设的值，与列注释和 `seed.sql` 都对不上。

选 (b') 而不是 (a)：`available_count` 是不带时间维度的单值，而「还剩几台」是
**(设备, 时段)** 的函数。写时扣减 = 用一维的量记二维的事实，周一借走一台会把
周二的名额一起吃掉；而且取消**和**完成两条路径都要记得回补，漏一条就单调递减到 0，
不报错、不进日志。

**`release_occupancy`：已定「删」并已执行（2026-09-28）**

按 (b')，取消单离开 `ACTIVE_ORDER_STATUSES` 即自动释放，这个 hook 本来就不需要做
任何事。已核实它**除空操作外什么都不做**（不回补库存、不改状态、不释放锁），调用方
**只有 `api/orders.py::cancel_order` 一处**。函数、调用点、两条 monkeypatch 观测用例
一并删除；原 TC-11 改为断言可观测结果（取消后同一时段同一设备能再下一单）。
判据文档 §6 记录了完整理由。

> **请集成组同步 `docs/test.md` 的 TC-11**：其描述仍写着「执行 `release_occupancy`
> hook」。属团队权威文档，模块 3 未擅自改动。

**设备维度索引：已由集成组补上（2026-09-28 main `98c54ea`）**

`reserve_order` 增加了 `idx_status_start (order_status, start_time)`，正是
`_device_conflicts` 的谓词形态（`order_status IN (活跃) AND end_time > :start
AND start_time < :end`）。它不在 `§6.6` 原文里，属集成组确认后的补充，已登记进
`tests/module3/test_config_alignment.py::_EXTRA_INDEXES`（该用例的「不多」断言现在
要求规范外的索引必须登记并写明依据）。**云库是否已建仍未复验** —— 取决于迁移
`b7f1c4a92e35` 有没有在云库跑过。

**设备维度的并发：已加锁，但云库未验证（2026-09-28）**

模块 4 报的 3b（3 协程跨三场地抢 cap=2 的设备，3 单全成）已在本地稳定复现
13/13 次，属实。修法是把设备行锁提前到 `§5.5` **第 2b 步**（紧随场地锁、在任何
非加锁读之前）。

**理由不是「补一把锁」那么简单**：只把设备行锁补到第 4 步校验处**仍然超卖** ——
InnoDB 的 `REPEATABLE READ` 里，读视图由**第一条非加锁读**建立，`FOR UPDATE`
不建立它。第 4 步之前已经有两处非加锁读（`db.get(SysUser, ...)`、
`_time_conflicts`），视图早钉死在对方提交之前；此时再等锁，**锁等到了视图也不
刷新**，数出来的重叠单还是旧的。一句话：锁了一行、却从另一张表的旧快照里读计数，
这把锁是白加的。完整分析见 `docs/available_count口径判据.md` §7。

⚠️ **这仍是权宜之计**，并且**扩了 `§5.5` 第 2 步的锁足迹**（原本只锁场地行），
请复核。根治办法是把设备占用**物化成行**：占用表 + `(device_id, start_time)`
唯一键，或让 `device_ids` 走生成列 / 多值索引 —— **要改 `§6.3` 表结构或索引
口径，仍等集成组给**。在那之前这一维是「尽力而为的正确性 + 不做性能承诺」。

## P3 · `reminder_scan` 时区裸奔且不幂等

**事实**

- `app/services/message_service.py:61`：`now = datetime.now()` —— 取的是**服务器进程的本地时间**，
  naive、无时区。
- `app/core/utils.py:7-12`：`parse_time` 用 `datetime.strptime`，产出的也是 **naive** datetime；
  写入库的 `start_time` 就是客户端字面量的 `YYYY-MM-DD HH:mm:ss`（`§5.1` 只规定了**格式**，
  没有规定时区）。
- `docs/seed.sql:22` 显式写了 `SET time_zone = '+08:00'` —— **种子数据是按东八区墙上时钟灌进去的**。
  也就是说团队事实上的口径是 `Asia/Shanghai`，但**应用侧没有任何地方强制这一点**，
  库里也没有存储时区信息。这正是不一致会静默发生的原因。
- `reminder_scan` 用 `now` 与 `start_time` 直接比较（`:66-67`）。
- **不幂等**：每次调用都对窗口内每个已确认订单 **新建一条** `notify_message`
  （`:72-80` → `create_message` 每次 `db.add` 新的行），没有任何去重键或「已提醒」标记。

**为什么是问题**

1. **时区**：客户端（手机）按自己的墙上时钟提交 `start_time`；后端若跑在 UTC 容器里，
   `datetime.now()` 比客户端时钟快/慢 8 小时，提醒窗口就会**整体偏移** —— 要么提前 8 小时
   提醒，要么全部漏掉。本地开发机与云主机时区一致时**完全看不出来**，只在容器化部署时炸。
2. **重复推送**：调度器按分钟粒度跑（或 `POST /messages/remind` 被重复调用）时，
   同一订单会被反复提醒。窗口内每个订单每扫一次就多一条 —— 演示时消息列表会瞬间刷屏。

**需要定的是**

- 时区口径：统一按 `Asia/Shanghai` 落库（并在 `§5.1` 补一句），还是全链路改用带时区的
  UTC 存储 + 展示层转换？这会影响**所有**跨模块的时间比较，不只是提醒。
- 幂等口径：用 `notify_message` 上加唯一键 `(order_id, notify_type, 提醒窗口标识)`，
  还是新增一张 `reminder_log`？**注意这涉及 `§6.3` 表结构变更，需要集成组定。**

**模块3 的建议**：时区取「全链路 `Asia/Shanghai`」并在 `§5.1` 写明 —— 改动最小，
与现有 naive 存储兼容，只需把 `datetime.now()` 换成 `datetime.now(ZoneInfo("Asia/Shanghai"))`
并去掉 tzinfo 后比较。幂等用 `notify_message` 上的唯一键，比新增表改动小。

**需要什么答复**：时区口径；幂等键放哪张表（涉及 `§6.3` 变更，需要拍板）。

## P4 · `POST /messages/remind` 无任何鉴权

**事实**

- `app/api/messages.py:93-101`：`remind()` 的依赖只有 `db`，
  **没有 `get_current_user`、没有任何密钥校验**。
- 对比同文件其他端点：`unread_count`、`list_messages`、`read_message`、`read_all`
  **全部**带 `Depends(get_current_user)`（`:34、:49、:68、:82`）。只有这一条是裸的。
- 全仓库**没有全局鉴权中间件**（`app/main.py` 只注册了 CORS），
  `get_current_user` 是逐路由依赖 —— 所以「没写」等于「完全公开」。

**为什么是问题**

任何人都能 `POST /api/v1/messages/remind`，触发一次**全量**提醒扫描：对所有用户、
所有窗口内已确认订单，各生成一条通知并尝试 WebSocket 推送。结合 P3 的不幂等，
这是一个**零成本的通知轰炸 / 写放大**入口，且会污染演示数据。

**需要定的是**：调度器的身份用什么？

| 方案 | 说明 |
| --- | --- |
| (a) 共享密钥 | 配置项（如 `settings.reminder_secret`），请求头带 `X-Scheduler-Secret`；密钥由集成组下发 |
| (b) 内网限制 | 该路由只监听内网 / 由网关做 IP 白名单（需要网关配合） |
| (c) 不暴露 HTTP | 删掉该路由，提醒扫描只由进程内定时任务调用 `reminder_scan()` |

**模块3 的建议**：取 (c) + 保留 (a) 作为演示入口。理由：定时任务本来就在同一个进程里，
没必要为此开一个 HTTP 口；演示需要手动触发时再用密钥保护的入口。
**无论取哪个，在密钥/网关就位之前，本模块建议先按「未配置密钥即拒绝」的 fail-closed
方式实现**，避免这个口子一直敞着 —— 只要集成组确认默认值，我们立刻补上。

**需要什么答复**：取哪个方案；若取 (a)，密钥怎么下发、配置项叫什么名字对齐。
