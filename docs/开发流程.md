# AI全感知·智能空间与设备综合调度平台 项目文档（最终版）

---

## 一、项目概述

### 1.1 项目定位

面向企业的空间硬件资源智能调度 Web + 小程序双端系统。AI 为核心决策引擎，系统支持口语、拍照、手绘草图等模糊、带冲突约束的业务需求，由 LangChain Agent 完成解析、冲突校验、权衡决策、生成方案并写入业务数据库。

### 1.2 移除 AI 后流程中断场景

移除 AI 后，以下场景直接中断：

1. 用户口述"周五下午要个能坐 40 人的展厅带双投影，预算 1000 以内，没大场地就拆两个小的"——系统无法理解，预约流程无法启动。
2. 用户拍摄手绘草图表达布局诉求——系统无法解析，无法生成约束。
3. 管理员拍摄设备照片——系统无法判断损坏状态，工单无法自动生成。
4. 定时任务扫描订单——系统无法识别软冲突与资源浪费，预警失效。

### 1.3 核心架构

- 感知层：手机摄像头 / 麦克风
- 决策层：大模型 Agent + LangChain 编排
- 执行层：业务系统自动落库、工单流转、消息通知、数据分析

### 1.4 终端形态

- PC Web 管理端：Vue3
- 微信小程序端：Uni-app

### 1.5 用户角色

- 普通使用者
- 资源管理员
- 系统管理员

### 1.6 业务覆盖资源

1. 空间资源：会议室、展厅、多功能厅、户外活动场地；包含容量、配套硬件、位置、预算、开放时段属性。
2. 硬件设备资源：投影仪、音响、直播设备、显示屏、无人机、会议终端等可预约借用设备。
3. 完整业务链路：多模态需求输入 → Agent 智能调度决策 → 预约订单生成 → 资源锁定 → 移动端现场巡检运维 → AI 冲突预警 → 智能消息通知 → AI 运营数据分析报告输出。

### 3.3 LangChain 1.x 使用规范

- 使用 `langchain==1.3.11`、`langchain-openai==1.5.0`、`langchain-classic==1.0.0`
- Agent 创建统一使用 `langchain.agents.create_agent`
- 旧版 Chains/Retrievers 按需从 `langchain_classic` 导入
- FastAPI 端点必须使用 `async def`，调用 `ainvoke()` / `astream()`，禁止同步 `invoke()`
- 不训练、不微调任何大模型，不本地运行 7B 及以上大权重模型
- 所有 AI 能力依靠 API + LangChain 1.x 应用层编排实现
- `create_agent` 底层依赖 `langgraph` 与 `langgraph-checkpoint`，由 LangChain 1.x 隐式安装。自定义 Tool 的状态传递与 Agent 执行图遵循 LangGraph State 模型，开发时以 `create_agent` 封装为准，不直接操作底层 State
- 思考日志与 LangGraph 映射：Agent 执行过程中，`messages` 列表内的 `AIMessage`（含 `tool_calls`）和 `ToolMessage` 需按顺序映射为 `agent_trace` 的 Thought-Action-Observation 结构，落库 `reserve_order.agent_trace`

### 3.4 数据库驱动规范

- 统一使用异步驱动 `asyncmy==0.2.10`，禁止使用同步驱动 `PyMySQL` / `mysqlclient`
- SQLAlchemy 使用 `create_async_engine` 创建引擎，配合 `AsyncSession` 和 `async_sessionmaker`
- FastAPI 依赖注入 `get_db` 必须定义为 `async def`
- Tool 不直接操作数据库：LangChain Tool 函数通过调用 `services/` 层异步函数完成数据读写，禁止在 Tool 内直接使用 `AsyncSession`
- 连接串固定为 `mysql+asyncmy://`，禁止使用 `mysql+pymysql://`

### 3.5 环境配置规范

- 所有敏感配置（API Key、数据库密码、JWT 密钥）通过 `.env` 文件注入
- `.env` 文件严禁提交至 Git 仓库
- 提供 `.env.example` 模板，列出所有必需配置项，不含真实值
- 模型名称与 API 版本在 `.env` 中集中配置

### 4.3 模块间调用规范

- 业务接口与 AI 能力接口严格分离
- AI 中台只输出建议、方案、文案
- 所有数据写入数据库必须经过业务服务层校验
- Agent 通过 Tool 调用 `services/` 层异步函数访问业务数据，Tool 不直接操作数据库
- 统一异常处理：API 调用失败、大模型返回格式错误、图片解析失败均设置友好降级提示

### 4.4 各模块 AI 触点说明

#### 模块 1：语音输入

- ASR 转文本后增加 AI 语义规整，把口语转为结构化约束
- 示例："嗯……那个周五下午吧，大概四十来号人" → "时间：周五下午；人数：约 40"
- 规整失败时降级为原始文本，送 Agent 兜底

#### 模块 2：摄像头空间感知

- 识别结果附带 AI 置信度评分
- 置信度低于阈值时，AI 主动生成追问文案："识别到可能是 A 栋 3 楼展厅，置信度 65%，是否正确？"
- 用户确认后进入 Agent，否认则重拍或改文字输入

#### 模块 3：移动端预约与通知

- 预约创建后，AI 自动生成预约摘要卡片
- 示例："周五 14:00-16:00 使用 A 栋 3 楼展厅，含双投影与音响，预算 980 元"

#### 模块 4：核心调度 Agent

5 个典型决策场景：

| 场景       | 输入                          | AI 决策                         | 规则为何不行             |
| ---------- | ----------------------------- | ------------------------------- | ------------------------ |
| A 预算降级 | 预算 800，需求 40 人 + 双投影 | 优先保场地，降级投影为单投影    | 规则无法权衡优先级       |
| B 场地拆分 | 无 40 人场地，要求拆两个小的  | 拆为 2 个 20 人会议室，时段对齐 | 规则无法自主决定拆分策略 |
| C 设备替代 | 投影仪全占用，需求含投影      | 推荐替换为 LED 显示屏           | 规则无法判断"可替代"     |
| D 需求矛盾 | 人数 40 但预算 500            | 指出矛盾，给出 3 条修改建议     | 规则无法生成自然语言建议 |
| E 活动合并 | 同团队连续两场活动            | 建议合并为一个时段，节省资源    | 规则无法识别"可合并"模式 |

#### 模块 5：资源与设备管理

- 新增资源时，AI 根据名称与描述自动推荐标签（如"适合培训""适合发布会"）
- 示例：输入"A 栋 3 楼大房间，可坐 40 人，有投影"，AI 推荐标签"展厅、培训、发布会"
- 标签用于 Agent 检索时过滤

#### 模块 6：AI 智能巡检

- 增加 AI 生成维修建议：识别到"投影仪灯泡老化"，自动生成"建议更换灯泡，型号 X"
- 增加 AI 生成巡检摘要：一次巡检多张照片，AI 汇总成一段话
- 示例："本次巡检 8 台设备，7 台完好，1 台投影仪灯泡老化需更换"

#### 模块 7：AI 冲突预警与智能通知

明确区分两类冲突：

| 类型   | 检测方               | 示例                                                         |
| ------ | -------------------- | ------------------------------------------------------------ |
| 硬冲突 | 事务校验（后端算法） | 同一场地同时段重复预约                                       |
| 软冲突 | AI 扫描              | 同团队连续活动无休息、高价值设备被低优先级占用、容量远超需求 |

AI 只负责软冲突，硬冲突由事务兜底。

#### 模块 8：AI 数据洞察面板

强制 AI 输出结构化建议，每条包含三要素：

```json
{
  "finding": "周三 14:00-16:00 展厅使用率 100%",
  "evidence": "该时段有 5 条预约，全部为已确认状态",
  "suggestion": "建议将其中 2 场活动移至周四同时段，周四使用率仅 20%"
}
```

#### 模块 9：用户认证与权限

- 登录时增加 AI 异常检测：识别异常登录行为（异地、频繁失败）
- 示例：同一账号 5 分钟内从两个城市登录，AI 触发告警并锁定
- 作为可选增强，不影响主流程

#### 模块 10：系统集成与联调

- 增加 AI 调用监控面板：实时展示 Agent 调用次数、成功率、平均耗时
- 演示时可切换至此面板，展示"AI 在真实运行"的证据

## 五、接口规范

### 5.1 通用规范

- 所有后端接口统一以 `/api/v1/` 开头
- 请求方式严格遵守 `GET`（查询）、`POST`（新增/复杂查询）、`PUT`（修改）、`DELETE`（删除）
- 请求头统一：`Content-Type: application/json`
- 认证头：`Authorization: Bearer {token}`
- 时间格式统一：`YYYY-MM-DD HH:mm:ss`
- 布尔值统一：`true` / `false`，禁止使用 0/1
- 身份来源：`userId`、`inspectorId`、`handlerId` 等身份标识一律从 JWT 解析，禁止从请求体或 FormData 传入，防止身份伪造

### 5.2 统一响应体

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

5.3 接口契约中 `→` 后一律指 `data` 字段内容。

### 5.3 接口契约清单

#### 模块 1：语音输入

- `POST /api/v1/voice/asr`：FormData 上传音频文件 `file` → `{ "text": "..." }`
- `POST /api/v1/voice/format`：`{ "rawText": "..." }` → `{ "formattedText": "...", "keywords": [] }`

#### 模块 2：摄像头空间感知

- `POST /api/v1/image/analyze`：FormData 上传图片 `file` → `{ "type": "space", "spaceId": 101, "spaceName": "...", "confidence": 0.92, "availableTime": [], "devices": [] }`
- `POST /api/v1/image/sketch`：FormData 上传图片 `file` → `{ "type": "sketch", "capacity": 30, "layout": "...", "requirements": [], "confidence": 0.85 }`

#### 模块 3：移动端预约与通知

后端 FastAPI 必须在 API 网关层统一配置 CORS，允许前端 `localhost` 及小程序域名访问。

### 5.5 数据库事务与并发控制规范

Agent 自动创建预约时，必须在一个数据库事务中完成资源锁定，防止并发冲突。具体实现顺序：

1. `BEGIN` 事务
2. `SELECT ... FOR UPDATE` 对目标 `space_resource` 行加锁
3. 校验时间重叠：查询 `reserve_order` 中该场地在目标时段是否存在已确认订单
4. 校验设备可用性
5. 插入 `reserve_order`，写入 `device_ids`
6. `COMMIT`

若第 3 步或第 4 步校验失败，`ROLLBACK` 并返回友好提示。

### 6.7 表结构变更 DDL 清单

以下 `ALTER TABLE` 由基础支撑与集成组统一执行。执行前需知会业务中台组（涉及 `inspect_record`、`repair_ticket`）。

```sql
-- 1. space_resource 新增字段
ALTER TABLE space_resource
  ADD COLUMN space_type INT NOT NULL DEFAULT 1 COMMENT '1会议室 2展厅 3多功能厅 4户外场地' AFTER space_name,
  ADD COLUMN status INT NOT NULL DEFAULT 1 COMMENT '1可用 0停用' AFTER open_end_time;

-- 2. space_resource 开放时段拆分
ALTER TABLE space_resource
  ADD COLUMN open_start_time TIME NULL AFTER budget,
  ADD COLUMN open_end_time TIME NULL AFTER open_start_time;

UPDATE space_resource
SET open_start_time = '08:00:00', open_end_time = '22:00:00'
WHERE open_time IS NOT NULL;

ALTER TABLE space_resource DROP COLUMN open_time;

-- 3. device_resource 新增数量字段
ALTER TABLE device_resource
  ADD COLUMN total_count INT NOT NULL DEFAULT 1 AFTER device_status,
  ADD COLUMN available_count INT NOT NULL DEFAULT 1 AFTER total_count;

-- 4. inspect_record 新增 space_id
ALTER TABLE inspect_record
  ADD COLUMN space_id BIGINT UNSIGNED NULL AFTER id,
  ADD CONSTRAINT fk_inspect_space FOREIGN KEY (space_id) REFERENCES space_resource(id);

-- 5. repair_ticket 新增设备/空间关联
ALTER TABLE repair_ticket
  ADD COLUMN device_id BIGINT UNSIGNED NULL AFTER inspect_id,
  ADD COLUMN space_id BIGINT UNSIGNED NULL AFTER device_id,
  ADD CONSTRAINT fk_ticket_device FOREIGN KEY (device_id) REFERENCES device_resource(id),
  ADD CONSTRAINT fk_ticket_space FOREIGN KEY (space_id) REFERENCES space_resource(id);

-- 6. notify_message 新增通知类型与关联订单
ALTER TABLE notify_message
  ADD COLUMN notify_type INT NOT NULL DEFAULT 1 COMMENT '1预约提醒 2变更致歉 3故障告警' AFTER receiver_id,
  ADD COLUMN order_id BIGINT UNSIGNED NULL AFTER notify_type,
  ADD CONSTRAINT fk_notify_order FOREIGN KEY (order_id) REFERENCES reserve_order(id);

-- 7. 索引创建
CREATE INDEX idx_space_type ON space_resource(space_type);
CREATE INDEX idx_capacity ON space_resource(capacity);
CREATE INDEX idx_device_type ON device_resource(device_type);
CREATE INDEX idx_space_time ON reserve_order(space_id, start_time, end_time);
CREATE INDEX idx_status ON reserve_order(order_status);
CREATE INDEX idx_space_id ON inspect_record(space_id);
CREATE INDEX idx_device_id ON repair_ticket(device_id);
CREATE INDEX idx_ticket_status ON repair_ticket(ticket_status);
CREATE INDEX idx_receiver_read ON notify_message(receiver_id, is_read);
```

### 7.1 通用规范

## 九、安全规范

### 9.1 认证与授权

- 使用 JWT 双 Token 机制（accessToken + refreshToken）
- Token 自动续期
- RBAC 权限模型：角色-权限-用户绑定
- 区分普通用户、资源管理员、系统管理员
- 身份一律从 JWT 解析，禁止从请求体或 FormData 传入身份标识

### 9.2 数据安全

- 密码使用 bcrypt 加密存储，锁定 `bcrypt==4.0.1`
- 敏感配置通过环境变量注入，不硬编码
- API 接口必须校验权限
- 防止 SQL 注入，使用 ORM 参数化查询

### 9.3 AI 安全

- Agent 只能通过 Tool 调用 `services/` 层访问业务数据，禁止直连数据库
- 大模型输出必须做业务边界校验，防止 AI 幻觉
- 图像识别只做业务需求解析，业务真实性由后端校验
- 消息推送只负责生成文案，业务状态变更由后端控制
- 内部 Tool 禁止注册为公开 HTTP 端点

### 9.4 云数据库安全

- 云服务器 MySQL 仅对团队开发人员 IP 开放访问
- 数据库密码由基础支撑与集成组统一管理，定期更换
- 禁止将数据库连接信息写入代码、文档或提交至仓库
- 文档中所有连接信息使用占位符，真实值仅存于 `.env`

## 十二、部署与运维规范

### 12.1 环境要求

- 阿里云 ECS 2 核 2G，Ubuntu 22.04
- MySQL 8.0.39 部署于云服务器，端口从 `.env` 读取
- Redis 7.2.5 部署于云服务器
- Nginx 1.26.2 反向代理
- 可选 Docker 26.1.4 + Docker Compose 2.29.7
- 内存限制：2 核 2G 同时跑 MySQL + Redis + Nginx + Uvicorn，必须配置 2G swap，并限制各服务内存上限

### 12.2 环境区分

| 环境 | 数据库                               | 用途         |
| ---- | ------------------------------------ | ------------ |
| dev  | `smart_scheduler_dev`                | 日常开发联调 |
| test | `smart_scheduler_test`               | 自动化测试   |
| prod | `smart_scheduler_prod`（部署时创建） | 演示与验收   |

环境切换通过 `.env` 中 `DB_NAME` 控制，禁止在代码中硬编码。

### 12.3 部署流程

- 后端：激活 conda 环境 `smart_dev`，`pip install -r requirements.lock`，使用 Uvicorn 启动，数据库连接从 `.env` 读取
- 前端：使用 `npm ci` 安装依赖，构建后由 Nginx 托管
- 数据库：云服务器上已创建 `smart_scheduler_dev`，表结构与索引已就绪
- Redis：在云服务器上启动服务，配置持久化

### 12.4 数据迁移流程

1. 集成组编写 DDL 脚本，提交至 `docs/database.md`
2. 执行前备份当前库：`mysqldump -u smart_dev -p smart_scheduler_dev > backup_$(date +%Y%m%d).sql`
3. 在测试库 `smart_scheduler_test` 先执行，验证无误
4. 在开发库 `smart_scheduler_dev` 执行，通知全体成员
5. 更新 `docs/database.md` 记录变更

### 12.5 备份策略

- 每日自动备份：`mysqldump` + cron，保留 7 天
- 每次 DDL 执行前手动备份
- 备份文件存于云服务器 `/backup/` 目录，不上传至 Git

### 12.6 运维规范

- 监控指标：CPU、内存、磁盘、接口响应时间、Agent 调用成功率
- 告警阈值：CPU > 80%、内存 > 90%、接口 P95 > 2s、Agent 成功率 < 90%
- 告警渠道：飞书群机器人
- 日志：JSON 格式，按天切分，保留 30 天

## 十三、风险管理规范

| 风险点                           | 应对方案                                                     |
| -------------------------------- | ------------------------------------------------------------ |
| 大模型幻觉，编造不存在的场地设备 | Agent 只调用 Tool 查询真实业务数据；后端业务接口做二次校验，拒绝非法参数入库 |
| 多模态图像识别识别错误           | 增加置信度评分与追问；识别失败友好提示用户改用文字输入需求   |
| API 网络超时                     | 设置超时时间，友好降级提示，缓存已有 Agent 中间结果，支持重试 |
| 服务器算力不足                   | AI 全部调用公有云端 API；阿里云 ECS 只运行业务接口、数据库，不跑大模型推理 |
| Agent 输出 JSON 格式错乱         | 后端增加 JSON 解析容错，Prompt 强制约束输出格式，异常则返回文本自然语言结果 |
| 依赖版本冲突                     | 严格锁定版本号，使用 `requirements.lock` 全量锁定；CI 构建时校验一致性 |
| LangChain 1.x 异步调用冲突       | FastAPI 端点必须使用 `async def`，调用 `ainvoke()` / `astream()`，禁止同步 `invoke()` |
| 数据库驱动同步异步冲突           | 统一使用 `asyncmy==0.2.10` 异步驱动，连接串固定 `mysql+asyncmy://` |
| bcrypt 不兼容                    | 锁定 `bcrypt==4.0.1`，严禁升级到 5.x                         |
| 测试污染正式库                   | 使用独立测试库 `smart_scheduler_test`，或事务内回滚          |
| 服务器内存不足                   | 配置 2G swap，限制各服务内存上限                             |
| 表结构与契约不一致               | 按 6.7 DDL 清单统一变更，变更前知会业务中台组                |
| Git 合并冲突                     | 遵循分支策略，每个功能从 develop 创建 feature 分支；推送前先拉取最新代码 |
| 敏感信息泄露                     | `.env` 加入 `.gitignore`；API Key 通过环境变量注入；文档使用占位符 |
| 云数据库连接失败                 | 确认 IP 白名单、端口开放、账号密码正确；使用统一配置         |
| 身份伪造                         | 身份一律从 JWT 解析，禁止从请求体传入                        |

### 13.1 演示应急预案

| 演示中可能出现  | 应急动作                                                       |
| --------------- | -------------------------------------------------------------- |
| 多模态识别失败  | 切换预置图片，展示识别成功流程                                 |
| Agent 响应超时  | 切换预置 trace，展示思考过程                                   |
| 大模型 API 欠费 | 切换假 LLM 夹具，展示流程完整性                                |
| 云数据库断连    | **前端回放预置 trace**，展示思考过程与方案（见 13.1.1）        |

#### 13.1.1 云数据库断连：回放预置 trace（原「本地 SQLite 镜像库」已废弃）

**决定**（2026-09-28，集成组）：砍掉「切换本地 SQLite 镜像库」，改用**前端回放预置 trace**。

**数据源**：`docs/mock/agent_schedule.json`（7 步 / 39 秒）。
它是**唯一真源**，与屏 3 的思考链渲染、`POST /api/v1/mock/agent/schedule` 三处共用同一份。
前端两种取法，按现场情况选：

1. 后端还活着（**数据库断连不影响后端启动** —— 启动探活失败只打日志，见
   `app/main.py` 的 `_probe_database`）→ 直接调 `POST /api/v1/mock/agent/schedule`
   （该路由仅在 `DEBUG=true` 时注册）；
2. 后端整体不可用 → 用前端自带的同一份 trace 副本。
   副本必须**取自这份 json**，形状（步数、严格递增的时间戳、`ScheduleData` 字段）
   已由后端 `tests/api/test_agent_schedule_mock.py` 钉住，可据此核对副本有没有过期。

**为什么废弃镜像库**：

- 云库 9 张表、11 个索引、种子数据都要在本地重建一遍，等于演示前临时维护
  第二套 schema —— 它一偏离，演示跑的就是另一个系统；
- MySQL 方言（`JSON_ARRAY`、`ON DUPLICATE KEY UPDATE`、`CURDATE()+INTERVAL`）
  与 `SELECT ... FOR UPDATE` 行锁语义在 SQLite 上**不等价**，
  镜像库「能跑起来」不等于演示可信；
- 切换动作本身要改 `.env`、重启服务、灌数据，这几步都在演示当口执行，
  是引入新故障的窗口。而回放 trace 不需要数据库，是**可靠性最高**的那条路。
