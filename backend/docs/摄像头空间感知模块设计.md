## 一、模块定位与边界

### 1.1 模块做什么

按 §4.2 与 §4.4 模块 2 的定义，本模块只负责两件事：

1. **现场拍照识别空间 / 门牌** —— 用户拍摄房间、门牌、场地全景照片，AI 判断"这是哪个场地"，给出**置信度评分**；置信度不足时**主动生成追问文案**让用户确认。
2. **手绘草图识别与空间布局解读** —— 用户手绘布局草图（圆桌/剧院式/分区），AI 解读出**预估人数、布局形式、隐含约束**。

### 1.2 模块不做什么（边界）

| 不做的事 | 归属 | 原因 |
| --- | --- | --- |
| 不生成预约方案、不选场地、不锁定资源 | 核心调度 Agent（模块 4） | 本模块**只输出感知结果**（§4.3：AI 中台只输出建议、方案、文案） |
| 不写 `reserve_order` / 不锁库存 | 业务中台组 | §5.5 事务与并发控制属于业务服务层 |
| 不判断设备"损坏" | AI 智能巡检（模块 6） | 本模块只识别"照片里有哪些**设备类型**"，损坏判定与工单是模块 6 的链路 |
| 不做场地 CRUD | 资源与设备管理（模块 5） | 本模块只**读** `space_resource`，不写 |
| 不做语音/文本规整 | 语音输入（模块 1） | 两条独立感知链路，最终都汇入 Agent |

**一句话边界**：本模块 = **图像 →（结构化感知结果 + 置信度）**，输出物是给 **Agent / 小程序 UI** 消费的中间态，不是业务终态。

### 1.3 在 AI 闭环中的位置

```
[小程序摄像头] ──拍照──► POST /api/v1/image/analyze
                              │
                              ▼
                    ┌─────────────────────┐
                    │  多模态大模型（视觉） │  ← 本模块核心
                    │  空间匹配 + 置信度自评 │
                    └─────────────────────┘
                              │  结构化输出（双策略兜底）
                              ▼
                    ┌─────────────────────┐
                    │  后端业务边界校验     │  ← 防幻觉关键
                    │  用 DB 权威数据覆盖   │
                    └─────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
    confidence ≥ 阈值                  confidence < 阈值
    直接返回 spaceId + 详情            返回 needConfirm + question
              │                               │
              └───────────────┬───────────────┘
                              ▼
                    POST /api/v1/agent/schedule   ← 模块 4
                    （imageContext 作为上下文传入）
```

更详细的时序、数据形态变化与异常分叉见 **`docs/摄像头空间感知模块数据流转图.md`**。

## 三、关键设计决策

### D1：不使用 `create_agent`，采用单轮多模态调用

§3.3 规定"Agent 创建统一使用 `langchain.agents.create_agent`"，但那条规范针对的是**模块 4 核心调度 Agent**。

| | 直接调用多模态模型（**本模块采用**） | `create_agent` 包装 |
| --- | --- | --- |
| 任务形态 | 单轮、无工具调用、无多步推理 | 多轮、需调工具、需状态机 |
| 模型调用次数 | 恒定 1 次 | ≥1，取决于工具调用轮数 |
| 输出可控性 | 高，格式由 schema 保证 | 低，Agent 会自行组织语言，**可能破坏 JSON 契约** |
| 延迟 | 可预测 | 至少翻倍 |
| `agent_trace` | 单轮没有 Action/Observation，无 trace 可存 | 天然产出 Thought-Action-Observation |

**结论**：模块 2 是「感知」而非「决策」。没有工具可调时，`create_agent` 的循环第一次迭代就 `END`，退化成一层壳包着单轮调用，只增加不确定性。备选方案与代价见附录 A3。

### D2：模型只做候选匹配，后端做权威校验（防幻觉的核心）

§9.3 明确："图像识别只做业务需求解析，业务真实性由后端校验"；§13 风险表第一条："大模型幻觉，编造不存在的场地设备"。

落地方式（`image_service._match_candidate`）：

1. 调模型**之前**，先从 `space_resource` 查出候选场地（`status=1`），**注入 Prompt**，要求"只能从列表里选，一个都不像就填 null"。
2. 模型返回后，**再一次**在候选集合中核对，匹配优先级为：`spaceId` 命中 → 名称完全一致 → 名称互相包含且**唯一**命中。
3. `spaceName` / `capacity` / `location` 一律**用数据库的值回填**，不采用模型输出。

这样即使模型完全胡言乱语，接口也**不可能**返回一个不存在的场地 id。名称模糊匹配时若出现歧义（如"A栋3楼展厅"与"B栋3楼展厅"都匹配"3楼展厅"），**不猜**，返回未匹配交用户确认。

### D3：候选列表注入 Prompt（而非自由识别后模糊匹配）

| 方案 | 采用 | 理由 |
| --- | --- | --- |
| A. 模型自由识别文字 → 后端 `LIKE` 匹配 | ✗ | 中文门牌千奇百怪，匹配率低，演示易翻车 |
| **B. 候选列表注入 Prompt，模型做选择题** | **✓** | 命中率高、可解释、演示稳定 |
| C. 向量检索 + RAG | ✗ | **本项目明确不引入向量库**；且 8 个场地属过度设计 |

方案 B 加**候选数量上限**（`IMAGE_SPACE_CANDIDATE_LIMIT`，默认 100）防止 Prompt 爆炸。
注意：候选列表只含 `id/名称/类型/位置/容量`，**不含任何照片信息**，模型仍必须真的"看"照片才能做选择。

### D4：三级降级，任何一环挂掉都不返回 500

```
第 1 级：解析彻底失败        → 返回自然语言引导（guidance）+ confidence=0，绝不抛异常
第 2 级：模型调用超时/报错    → 转成业务异常 code=41003 + 友好提示
第 3 级：模型返回不存在的场地 → 丢弃幻觉结果，返回 needConfirm + 候选列表让用户自己选
```

### D5：全链路异步

§3.4 + §13 硬性要求：端点 `async def`、`await llm.ainvoke(...)`、`AsyncSession`。
本模块**任何位置都不得出现**同步 `invoke()`、`requests`、`pymysql`。
文件读写一律走 `aiofiles`，避免阻塞事件循环。

### D6：图片落盘，但落盘失败不阻断识别

- 落盘到 `backend/uploads/YYYYMMDD/<uuid>.<ext>`，返回可访问 URL，用于演示回放与答辩溯源。
- 文件名由服务端 uuid 生成，**再过一遍字符白名单清洗**（`_safe_stem`），形成防御纵深。
- 落盘用 `try/except` 包住：磁盘/权限问题只记日志并返回 `None`，识别主流程不受影响。
- 目录已加入 `.gitignore`。

### D7：不新增数据库表

§6.3 已定义的 9 张表中没有"图像识别记录表"，且 §6.5 说明"后续表结构变更须由集成组统一执行"。识别结果有时效性，不落库不影响业务；照片本身落盘即可。若后续确需留存，优先复用 `inspect_record`（已有 `image_url` + `ai_result` JSON 字段）。

### D8：结构化输出双策略（v2 新增，本版最重要的实现变更）

**策略 A（首选）**：`llm.with_structured_output(schema, include_raw=True)`

- 底层**仍然是一次** `ainvoke` —— 它把 Pydantic schema 翻译成 JSON Schema / function-calling 协议交给模型，再把返回解析成 Pydantic 对象。
- 格式由协议层保证，比"让模型自由输出 JSON 再自己解析"可靠得多。
- `include_raw=True` 是关键：即使结构化解析失败，我们**仍拿得到模型的原始文本**，可以从中抢救 JSON，而不是"什么都没拿到"。

**策略 B（兜底）**：普通 `ainvoke` + 手工 JSON 容错解析

- 用于模型/供应商不支持 tool calling / json_schema 的情况（部分视觉模型如此）。
- JSON 解析依次尝试：直接 `json.loads` → 剥离 ` ```json ` 围栏 → 正则截取最外层花括号。

**切换方式**：`.env` 的 `VISION_STRUCTURED_OUTPUT`。设为 `false` 即强制走策略 B，**无需改代码**。

**不重复调用**：策略 A 解析失败但拿到了原始文本时，**只做本地抢救，不再发第二次请求** —— 同样的 Prompt 再问一遍大概率还是同样结果，白白多花一次调用的钱和延迟。

### D9：schema 层做类型清洗（v2 新增，实测暴露的缺口）

实测中发现两个真实问题，均已修复：

1. **Pydantic 默认忽略多余字段** → 模型"答非所问"（把空间识别的字段塞给草图接口）时会被静默接受，产出一个"空但自信"的结果。
   - 修复：service 层增加**语义空结果判定** —— 三个核心字段全空即按"没读懂"处理，置信度归零。
2. **`requirements: list[str]` 过于严格** → 模型返回的数组里混进一个 `123`，就会让**整份响应**校验失败，连带丢掉本来可用的 `layout` 与 `capacity`。
   - 修复：在两个识别 schema 上增加 `model_validator(mode="before")`，把脏类型归一化（非字符串剔除、数字字符串转整数、不可解析的置 null）。
   - **关键点**：这些校验器不影响 `with_structured_output` 生成的 JSON Schema（Schema 从字段定义推导），所以**对模型依然严格，对解析足够宽容**。

## 四、接口契约

### 4.1 通用约定（§5.1 / §5.2）

- 前缀 `/api/v1/`，方法 `POST`（含文件上传）
- 请求头：`Content-Type: multipart/form-data`、`Authorization: Bearer {token}`（**必带**）
- 响应：统一响应体 `{ "code": 200, "message": "操作成功", "data": {...} }`
- 字段命名：数据库 `snake_case`，**API 传输一律 `camelCase`**（§6.2）
- 身份来源：**一律从 JWT 解析**，请求体中不接受任何 `userId`（§5.1）
- **HTTP 状态码约定**：所有响应 HTTP 状态码恒为 200，业务结果由 `body.code` 表达 —— 这样前端 axios 只需在一处拦截 `code !== 200`，不必处理非 2xx 抛错。**此约定待集成组确认**（见 §13）。

## 七、文件职责与关键实现要点

> v1 文档在此处贴了大段代码。代码已落地到实际文件中，**不再复制粘贴避免两处失同步**。此处只列每个文件的职责与最值得注意的实现点。

### 7.1 `app/core/llm.py`

- `get_vision_llm()` 用 `lru_cache(maxsize=1)` 做单例 —— 复用 httpx 连接池，2核2G 的 ECS 上省下反复握手的开销。
- **配置前置校验**：`.env` 没填 `VISION_MODEL_NAME` / `VISION_API_KEY` 时，直接抛出 `BusinessError(41003)` + 一句能照做的提示，而不是让底层抛一个看不懂的 `KeyError`。
- `reset_vision_llm_cache()` 供测试与将来的运行时热切换使用。
- ⚠️ `timeout` 参数在部分 langchain-openai 版本中名为 `request_timeout`，文件注释里写了应对方式。

### 7.2 `app/schemas/image.py`

三类模型：

1. **识别结果模型**（`SpaceRecognition` / `SketchRecognition`）—— 同时充当 `with_structured_output` 的 schema。每个字段的 `Field(description=...)` 会被翻译进 JSON Schema，是模型理解"该填什么"的**唯一依据**，因此写得非常具体。
2. **公共子结构**（`SpaceCandidate` / `AvailableSlot` / `DeviceHint`）。
3. **响应模型**（`SpaceAnalyzeData` / `SketchAnalyzeData`）—— 字段名直接用 camelCase 对齐契约，不做 alias 转换，让"代码 = 文档"。

**输入端清洗**（D9）：两个识别模型各有一个 `model_validator(mode="before")`，把脏类型归一化。

### 7.3 `app/agent/prompts/image_prompt.py`

- `build_space_analyze_messages(image_data_url, candidates, threshold)`
- `build_sketch_analyze_messages(image_data_url, threshold)`

要点：
- 候选列表在**无候选**时明确告知模型"应填 null"，避免它强行选一个。
- 判断依据按优先级排列：**门牌文字 > 空间形态 > 可见设备**。
- 追问文案由模型生成（§4.4），但后端另有模板兜底。
- 刻意**不放 few-shot 示例** —— 视觉任务的参考示例必须以图片形式给出，纯文本示例帮不上忙还占上下文。

### 7.4 `app/services/image_storage.py`

- `read_and_validate_image()`：MIME 白名单初筛 → **分块读取（64KB）并实时中断**（超限时不必读完全部）→ 魔数探测。
- **以魔数探测结果为准**，不信客户端声明的 Content-Type（可伪造）。两者不一致时记 warning 但放行 —— 既然魔数已证明它是图片，就没必要为难用户。
- `_safe_stem()`：文件名白名单清洗（`[^A-Za-z0-9_-]` 全部剔除），防御纵深。
- `save_image()`：**失败返回 `None` 而非抛异常**（D6）。

### 7.5 `app/services/image_service.py`（核心）

| 函数 | 职责 |
| --- | --- |
| `analyze_space_image` | 空间识别主流程 ①–⑦ |
| `analyze_sketch_image` | 草图识别主流程 ①–⑥（含语义空结果判定） |
| `_recognize` | **双策略模型调用**（D8），返回 `(parsed, raw_text)` |
| `_unpack_structured` | 拆解 `include_raw=True` 的返回结构 |
| `_normalize_message_text` | 内容块列表 → 纯文本（部分供应商返回 list） |
| `_extract_json` | 三重 JSON 容错解析 |
| `_validate_json_text` | 容错解析 + Pydantic 校验的组合 |
| `_match_candidate` | **防幻觉三方匹配**（D2） |
| `_clamp01` | 置信度裁剪 [0,1]，含百分数归一化（85 → 0.85） |
| `_clean_str_list` | 字符串数组清洗 |
| `_make_space_question` | 追问文案兜底模板 |
| `list_active_space_candidates` | 候选查询（只读 `status=1`） |
| `list_available_slots` / `_safe_list_available_slots` | 空档计算 + 异常降级包装 |

**空档算法**：取场地开放时段 `open_start_time ~ open_end_time`，减去 `order_status in (1, 2)`（待确认 + 已确认）的订单区间，逐日做区间减法。跨天订单按天边界裁剪。

### 7.6 `app/api/v1/image.py` 与 `app/main.py`

- 路由层只做三件事：参数注入、调用服务、包装统一响应体。**零业务逻辑、零 SQL、零 Prompt**。
- 两个接口都挂 `Depends(get_current_user)` 作为鉴权闸门（§5.1：身份只从 JWT 取）。
- 模型以 `Depends(get_vision_llm)` 注入 → 测试可用 `app.dependency_overrides` 整体替换。
- `main.py` 挂载：异常处理器、CORS、静态目录 `/uploads`、`image_router`、`/api/v1/health`。

| 认证头 | `header: { Authorization: "Bearer " + accessToken }`，**必须带**，否则 401 |
| 图片来源 | `uni.chooseMedia`，建议加 `sizeType: ["compressed"]` 压缩，避免超 5MB |
| 结果渲染 | `confidence` 以百分比展示（`(confidence*100).toFixed(0) + "%"`）；`rawText` 作辅助说明 |
| 追问交互 | `needConfirm === true` 时弹确认框：展示 `question`，提供"确认"/"重选"按钮；"重选"用 `candidates` 渲染列表 |
| 送 Agent | 用户确认后把整个 `data` 作为 `imageContext` 传给 `POST /api/v1/agent/schedule`（字段形状需与 Agent 组对齐） |
| 失败兜底 | 收到 41003 时展示"改用文字输入"入口（§4.4：否认则重拍或改文字输入） |
| 草图文案 | 在草图上传统筹加一句"请拍清晰、光线充足"，降低低置信度概率 |

## 附录 A：备选与预警方案

### A1. 若候选场地规模膨胀到几百个（**当前不实施**）

不再把全部候选注入 Prompt，改为：模型先自由识别门牌文字 → 后端 `LIKE` 检索 + 编辑距离排序取 Top-K → 第二轮把 Top-K 交给模型最终选择。

代价：两次模型调用，延迟翻倍。**当前 8 个场地不需要，仅作预案记录。**
（注：也**不会**引入向量检索 —— 本项目明确不使用向量数据库。）

### A2. 若需要"空间 ↔ 设备"关联（对应待确认问题 1）

需集成组新增关联表并执行 DDL（§6.5：表结构变更须由集成组统一执行）：

```sql
-- 仅作为讨论材料，未经评审，禁止直接执行
CREATE TABLE space_device (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  space_id BIGINT UNSIGNED NOT NULL COMMENT '空间ID',
  device_id BIGINT UNSIGNED NOT NULL COMMENT '设备ID',
  device_count INT NOT NULL DEFAULT 1 COMMENT '配套数量',
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_sd_space FOREIGN KEY (space_id) REFERENCES space_resource(id),
  CONSTRAINT fk_sd_device FOREIGN KEY (device_id) REFERENCES device_resource(id),
  UNIQUE KEY uk_space_device (space_id, device_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='空间配套设备关联表';
```

### A3. 若团队要求统一使用 `create_agent`（D1 的备选）

```python
from langchain.agents import create_agent

agent = create_agent(
    model=get_vision_llm(),
    tools=[],                      # 无工具：本模块不需要访问业务数据
    system_prompt=SYSTEM_PROMPT,   # 仍是 §7.2 的强约束 Prompt
)
result = await agent.ainvoke({"messages": messages})
# 之后仍需从 result["messages"][-1].content 里做结构化解析
```

**代价**：① 至少多一次模型调用，延迟与费用上升；② Agent 倾向于"自言自语"，破坏 JSON 契约的概率更高，容错逻辑要写得更厚；③ 与 §3.3「思考日志映射 `agent_trace`」的要求纠缠，而本模块并不需要 `agent_trace`。**不推荐。**
