## 三、分层架构

### 3.1 调用链

```
HTTP 请求
   ↓
[中间件]  CORS → RequestContext（请求 ID / 耗时 / 访问日志）→ AgentMetrics（埋点）
   ↓
[路由]    app/api/v1/*.py          只做三件事：声明入参出参、取依赖、调 service
   ↓
[依赖]    app/api/deps.py          认证（get_current_user）+ 授权（require_permission）
   ↓
[服务]    app/services/*.py        业务逻辑；★ 数据库写入的 commit 发生在这里
   ↓
[模型]    app/models/*.py          SQLAlchemy ORM
   ↓
[会话]    app/core/database.py     get_db：提供会话 + 结束时关闭（不 commit）
```

### 3.2 分层职责（**这条边界要守住**）

| 层 | 该做 | 不该做 |
| --- | --- | --- |
| 路由 `api/v1/` | 声明接口契约、取依赖、调 service、返回出参 | ❌ 写业务判断、❌ 直接操作数据库、❌ 拼 SQL |
| 依赖 `deps.py` | 认证、授权、拿到当前用户/门店等上下文 | ❌ 业务逻辑 |
| 服务 `services/` | 全部业务逻辑、**显式 commit**、抛业务异常 | ❌ 依赖 FastAPI 的 `Request`/`HTTPException` |
| 模型 `models/` | 表结构与关系映射 | ❌ 业务逻辑（字段定义**冻结**，见 8.4） |
| 核心 `core/` | 跨模块公共基建 | ❌ 依赖任何具体业务模块 |

**服务层不依赖 FastAPI**：`auth_service.py` 里没有 `HTTPException`，
它抛的是 `app/core/exceptions.py` 的 `BizError` 子类（如 `UnauthorizedError`）。
这样同一个服务既能被 HTTP 接口调用，也能被定时任务 / 脚本调用，且**单元测试不需要起 ASGI 应用**。

### 3.3 为什么用「纯 ASGI 中间件」

`request_context.py` 与 `agent_metrics.py` 都是**纯 ASGI**（`__call__(scope, receive, send)`），
不是 `BaseHTTPMiddleware`：

- `BaseHTTPMiddleware` 会为每个请求包一层 `anyio` 任务组，**与 SSE 流式响应冲突**
  （模块 4 的 Agent 链路要流式输出），且在高并发下有明显开销。
- 纯 ASGI 中间件直接转发 `send`，可以边收边转，对响应体零改动。

### 3.4 中间件顺序（**Starlette 是反向的**）

`add_middleware` 的行为是 **prepend**，所以**后加的在更外层**。最终从外到内：

```
CORS  →  RequestContext  →  AgentMetrics  →  ExceptionMiddleware  →  路由
```

本项目 `app/main.py` 的注册顺序**刻意**如此，因为：

- **CORS 必须在最外层**：否则 4xx/5xx 响应不会带 CORS 头，浏览器会把它显示成一个
  「没有任何信息的跨域错误」，而真实原因（如 401）被完全掩盖。
- **RequestContext 在 CORS 内层**：这样每个请求都能拿到 `X-Request-Id`，
  且错误响应也带这个头（便于按请求 ID 查日志）。

> ⚠️ **已知边界**：**框架级未处理异常**（例如响应模型校验失败）产生的 500
> **既没有 CORS 头也没有 `X-Request-Id`** —— 因为 Starlette 的 `ServerErrorMiddleware`
> 在最外层，它直接接管了响应。这由 `tests/api/test_cors.py` 的两个对照用例钉住
> （`test_unhandled_exception_response_has_no_cors_headers` 与
> `test_500_generated_inside_the_app_still_has_cors_headers`）。
> 对前端的影响：这类错误拿不到任何上下文，**必须看服务端日志**。

## 四、开发约定（必读）

### 4.1 统一响应体

**所有**接口（含错误）返回同一个信封（`开发流程.md` 5.1）：

```json
{ "code": 200, "message": "success", "data": { } }
```

实现：`app/core/response.py` 的 `ok()` / `error_payload()`；
异常由 `@app.exception_handler` 统一转成信封，**路由里不写 try/except**。

见 `docs/api.md` 第 1.2 节。**改动响应体形状 = 改动全组契约**，必须先公告。

### 4.2 错误码

规则：**错误码按段划分，HTTP 状态码跟随段位**（`开发流程.md` 5.2）。

| 段 | 类别 |
| --- | --- |
| `200` | 成功 |
| `400xx` | 参数/请求错误 |
| `401xx` | 未认证 |
| `403xx` | 已认证但无权限 |
| `404xx` | 资源不存在 |
| `409xx` | 状态冲突 |
| `429xx` | 限流 |
| `500xx` | 服务端错误 |
| `503xx` | 依赖不可用 |

**四个刻意的例外**（都有测试钉住）：

| 场景 | HTTP | 业务码 | 为什么 |
| --- | --- | --- | --- |
| 405 方法不允许 | 405 | **40000** | 复用「请求错误」段，透传 `Allow` 头 |
| 未知路由 404 | 404 | **40400** | 与「资源不存在」区分不了，统一走 404 段 |
| Pydantic 校验失败 | 400 | **40001** | 校验错误统一入口，`data.errors` 给字段级详情 |
| AI 输出非法 | 502 | **50001** | 上游返回了非法内容，属服务端问题 |

> ⚠️ **给前端的硬要求**：**按 `code` 分支，不要按 HTTP 状态码分支**。
> 例如 401 下藏着 7 个不同的业务码（40101 无令牌 / 40102 签名错 / 40103 过期 /
> 40104 类型错用 / 40105 已吊销 / 40106 未登记 / 40107 密码错），
> 前端对 40103 该去刷新、对 40107 该提示密码错 —— 只看 401 是分不出来的。

Add：新增错误码时，**必须同步** `app/core/error_codes.py` 的 `DEFAULT_MESSAGES`
与 `docs/api.md` 的错误码总表，并在 `tests/api/test_response_envelope.py` 的段一致性断言下验证。

### 4.3 字段命名：入出参 camelCase

- 数据库表名/字段名：`snake_case`（`开发流程.md` 6.2）
- **API 传输字段：`camelCase`**
- 幂等实现：出参模型继承 `CamelModel`（`app/core/camel.py`），
  用 `alias_generator=to_camel` + `populate_by_name=True`。

**三条必须记住的**：

1. **出参序列化必须 `by_alias=True`**。`model_dump()` 默认给 `snake_case`，
   漏了这个参数的表现是「成功响应是 `accessToken`、错误响应是 `access_token`」，
   前端只在报错时炸 —— 这是最难查的一类 bug。`app/core/response.py` 的
   `_json_response()` 里已经统一传了，**手写 dict 返回时要注意**。
2. **入参两种写法都收**（`populate_by_name=True`），所以前端传 `spaceId` 或 `space_id` 都行。
3. **未知字段忽略而非报错**（`extra="ignore"`），前端多传字段不该让接口 400。

> **为什么不用中间件做驼峰转换**：中间件重写 body 需要把请求体整个读进内存解析，
> **对 FormData 是灾难** —— 模块 1/2/6 上传图片时并发即 OOM；
> 而且会破坏模块 4 的 SSE 流式响应。这是当时排除中间件方案的决定性理由。

### 4.4 时间与金额

| 类型 | 传输格式 | 实现 |
| --- | --- | --- |
| 时间 | `YYYY-MM-DD HH:mm:ss`（**空格分隔，无 `T`，无毫秒，无时区后缀**） | `DateTimeStr` |
| 金额 | 两位小数的**字符串**（如 `"980.00"`） | `MoneyStr` |

```python
# 出参
class SpaceOut(CamelModel):
    open_start_time: DateTimeStr          # → "2026-09-27 09:30:00"
    budget: MoneyStr                      # → "980.00"
```

**两条纪律**：

- 时间统一用**本地 naive datetime（Asia/Shanghai）**，**禁止**散落 `datetime.utcnow()`。
  用 `app/utils/time_utils.py` 的 `now()`。
- 金额用**字符串**而不是 JSON number：`Decimal` 一旦变成 JSON number，
  前端 `JSON.parse` 会拿到 IEEE754 双精度，`980.09` 可能显示成 `980.0999999999999`。

> ⚠️ **已知边界（重要）**：入参**接受**带时区的 ISO 8601 字符串，但**照抄不换算**。
> 前端若传 `2026-09-27T09:30:00+08:00`，后端存进去的就是字面上的 `09:30:00`，
> 一旦前端用 `new Date().toISOString()` 生成时间（会转成 UTC），就会出现 **8 小时偏差**。
> 已在 `tests/unit/test_camel_and_datetime.py` 用带 ⚠️ 的用例钉住。
> **要求前端传 `YYYY-MM-DD HH:mm:ss`**（`docs/api.md` 1.5）。

### 4.6 身份来源

**当前用户身份只能来自 JWT**，不能来自 query 参数、请求体或请求头（那都是可伪造的）。

```python
from app.api.deps import CurrentUser, get_current_user

@router.get("/orders")
async def list_orders(user: CurrentUser = Depends(get_current_user)) -> ...:
    ...   # user.id / user.username / user.role_name / user.permissions
```

`CurrentUser` 是 **frozen dataclass**（不可变），且**每个请求都从数据库重新读角色**，
因此「改了角色立即生效、不需要重新登录」（有测试钉住）。

> `app/api/v1/auth.py` 的 `_client_ip()` 取 `X-Forwarded-For` **仅用于风控日志**，
> 该值**可伪造**，注释里已写明**绝不用于鉴权**。改动它之前请想清楚这一点。

## 五、新增接口的标准流程

> 照着做，不要跳步。**第 3 步和第 5 步最常被漏**。

### 步骤 1：定义 schema（`app/schemas/`）

```python
from app.core.camel import CamelModel, DateTimeStr

class SpaceCreateIn(CamelModel):
    name: str = Field(min_length=1, max_length=64)
    open_start_time: DateTimeStr

class SpaceOut(CamelModel):
    id: int
    name: str
    open_start_time: DateTimeStr
```

- 入参**必须**带约束（`min_length` / `ge` / `pattern`）—— 校验交给 Pydantic，
  不要写进 service 再抛异常。
- 出参**不要**包含敏感字段（密码哈希、内部标记）。

### 步骤 2：写服务（`app/services/`）

```python
async def create_space(db: AsyncSession, payload: SpaceCreateIn) -> SysSpace:
    space = SysSpace(name=payload.name, open_start_time=payload.open_start_time)
    db.add(space)
    await db.commit()          # ★ 见第 9 节：commit 是服务层的责任
    await db.refresh(space)    # 需要拿自增主键/默认值时
    return space
```

- 抛业务异常用 `app/core/exceptions.py` 的子类（如 `NotFoundError`、`ConflictError`），
  **不要**抛 `HTTPException`。

### 步骤 3：声明路由（`app/api/v1/<module>.py`）

```python
@router.post("/spaces", response_model=ApiResponse[SpaceOut], summary="创建场地")
async def create_space(
    payload: SpaceCreateIn,
    db: AsyncSession = Depends(get_db),
    user: CurrentUser = Depends(require_permission(Permission.SPACE_CREATE)),   # ★ 授权
) -> ApiResponse[SpaceOut]:
    space = await space_service.create_space(db, payload)
    return ok(SpaceOut.model_validate(space))
```

- **`Depends(require_permission(...))` 不能省**：每一个写接口都要有明确权限码。
- `summary` 用中文，会显示在 `/docs`。

### 步骤 4：注册路由（`app/api/v1/__init__.py`）

```python
router.include_router(space.router, prefix="/spaces", tags=["场地管理"])
```

> ⚠️ 漏了这一步的表现是：接口测试全绿（因为测试直接注册 router），
> 但**真实服务上 404**。`tests/api/test_response_envelope.py` 的
> `test_no_unregistered_non_api_routes` 会在「有路径没登记」时报警。

### 步骤 5：加权限码（`app/core/permissions.py`）

在 `Permission` 常量里加 `SPACE_CREATE = "space:create"`，并把它加入相应角色的清单，
否则**管理员也调不通**（权限判定只看权限码，不看角色名）。

### 步骤 6：写测试（`tests/`）

至少覆盖 **4 条**（`docs/test.md` 第八节）：

1. 正常流程
2. 参数校验失败 → 400 / 40001
3. 未鉴权 → 401 / 40101
4. 权限不足 → 403 / 40302（若需鉴权）

并在 `docs/test.md` 的对应章节登记用例。

### 步骤 7：更新文档

- `docs/api.md`：请求方式、路径、请求参数、响应示例（`开发流程.md` 11.2 强制要求）
- `docs/test.md`：登记用例
- 若涉及表结构 → `docs/database.md`

## 六、权限体系使用指南

### 6.1 权威来源

**`sys_role.permissions` 这个 JSON 字段是权限的唯一权威**（决策 3），
不是 `sys_permission` 表，也不是代码里的角色-权限映射。

| 位置 | 角色 |
| --- | --- |
| `sys_role.permissions` | ★ **权威**。鉴权只读它 |
| `app/core/permissions.py` 的 `ROLE_PERMISSIONS` | **仅作回落**：当库里的值为空（`NULL` / `[]` / `"[]"`）时才使用 |
| `sys_permission` 表 | 前端**菜单字典**，不参与鉴权（种子里刻意留空） |

**为什么这么设计**：鉴权一次查询就能拿到权限，不需要 join 三张表（用户→角色→权限）。
代价是权限数据没有外键约束，因此 `normalize_permissions()` 做了**极其宽容的容错** ——
它接受 21 种存储形态（JSON 数组、JSON 文本、权限位映射、逗号/分号/全角逗号/空格分隔的裸字符串……）。
这不是过度设计：`permissions` 字段是 `JSON` 类型，任何模块都可以往里写，
**容错在这里比严格更有价值**（严格会让一个手抖的写入变成 403 甚至 500）。

### 6.2 三个角色

| 角色名 | 权限数 | 定位 |
| --- | --- | --- |
| `admin` | 26 | 全部权限（含 `*` 通配） |
| `resource_admin` | 19 | 场地/设备/预约管理 |
| `user` | 10 | 普通用户 |

层次关系：`user(10) ⊂ resource_admin(19) ⊂ admin(26)`，**层层真有增量**
（`tests/unit/test_permissions.py::test_role_hierarchy_is_cumulative` 保证不是简单复制）。

### 6.3 权限码命名

`模块:动作`（决策 4），如 `space:create`、`device:delete`、`order:view`、`monitor:view`。

> ⚠️ **匹配是精确的，不做前缀匹配、不忽略大小写**：
> `order:view_all` **不**等于 `order:view`（有测试钉住）。
> 因此**不要把权限码写得只差一个后缀** —— `order:view` 与 `order:view_all` 是两个不同权限，
> 后者不会自动包含前者。

### 6.4 两种使用方法

```python
# 方式一：装饰单个接口（推荐，最明确）
@router.post("/devices", ...)
async def create_device(
    user: CurrentUser = Depends(require_permission(Permission.DEVICE_CREATE)),
): ...

# 方式二：判断当前用户是否具有某权限（用于分支逻辑）
if has_permission(user.permissions, Permission.ORDER_VIEW_ALL):
    ...  # 管理员看全部订单
else:
    ...  # 普通用户只看自己的
```

`require_role("admin")` 也存在，但**优先级低于权限码**：优先用权限码。
原因是角色名会变、权限码不会 —— 用角色名判断会让「给资源管理员加一个管理权限」
变成一次代码改动，而不是一次数据改动。

> ⚠️ **回落到静态映射的陷阱**：`effective_permissions()` **只在库值为空时**才回落。
> 所以把某角色的 `permissions` 改成 `["order:view"]`（**非空**）后，
> 该角色会**只剩这一个权限**，而不是「静态清单 + 这个权限」。
> 这是刻意的（改成少而真的权限应立即可见），但改数据时要知道这一点 ——
> 有测试 `test_permissions_revoked_in_the_database_stops_at_the_gate_immediately` 钉住。

### 6.5 当前接口的权限门禁

| 接口 | 门禁 |
| --- | --- |
| `POST /auth/login` | 无（登录本身） |
| `GET /auth/info` | 仅需登录 |
| `POST /auth/refresh` | 无（凭 refreshToken） |
| `POST /auth/logout` | 仅需登录 |
| `GET /monitor/agent` | **无鉴权**（见下） |
| `GET /health` / `GET /ready` | 无（探针） |
| 模块 1～8 的业务接口 | `/mock/*` 无鉴权；真实接口**必须**加 `require_permission` |

> ⚠️ **`/monitor/agent` 当前无鉴权，这是刻意的**：它是给可视化大屏（模块 8）与
> 演示用的聚合数字，模块 1～8 尚未实现，此时加门禁会让前端在联调期拿不到数据。
> **但这是一条有边界的决定**：一旦该接口要暴露**业务维度**（按用户/场地/订单的明细），
> **必须**加上 `require_permission(Permission.MONITOR_VIEW)`。
> `app/api/v1/monitor.py` 的注释里已写明这条边界。

### 7.1 Alembic 是 schema 的**唯一来源**（决策 1）

### 7.2 四个必知的坑

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| 用 `python -m alembic` | `No module named alembic.__main__` | **用 `alembic` 控制台脚本**。仓库根有同名 `alembic/` 目录，从根用 `-m` 启动会被它遮蔽 |
| 口令含 `%` | `InterpolationSyntaxError` | `env.py` 已把 `%` 转义成 `%%`，改拼装逻辑时别丢 |
| Windows 事件循环 | `asyncmy` 报错 | `env.py` 在任何 `asyncio.run` **之前**设置 `WindowsSelectorEventLoopPolicy` |
| 中文乱码 | `UnicodeEncodeError: 'gbk'` | `export PYTHONIOENCODING=utf-8` |

### 7.3 常用命令

```bash
cd <仓库根>                                  # 必须在根执行
alembic current                              # 当前版本
alembic upgrade head                         # 升到最新
alembic downgrade -1                         # 回退一版
alembic revision --autogenerate -m "描述"    # 生成迁移（★ 必须人工审查）
alembic upgrade head --sql                   # 只看 SQL，不执行
```

### 7.4 autogenerate 之后必须人工审查（**不要盲信**）

`alembic/env.py` 已经定制了两处，避免噪音，但它们**不能替代人工审查**：

| 定制 | 作用 |
| --- | --- |
| `_compare_type` | **忽略 `BIGINT` ↔ `BIGINT UNSIGNED` 的差异**（模型是 signed，云库是 unsigned，见 8.4） |
| `_include_object` | 阻止对**反射出来的索引**生成 `drop_index`（防误删手工 DDL 建的索引） |

审查清单：

```
[ ] 没有意料之外的 drop_table / drop_column
[ ] 没有意料之外的 drop_index（这是最危险的：索引丢了性能塌方但不报错）
[ ] 新增列的 server_default 是否正确（已有数据的表加 NOT NULL 列必须给默认值）
[ ] 迁移的 upgrade 与 downgrade 是否对称
[ ] 是否幂等（对已有对象重复执行不报错）—— 云库现状无法确认，幂等是必须的
```

### 7.5 迁移链与幂等索引

```
8969262c9d0c  init_tables_single_role         ← 9 张表（已存在）
b7f1c4a92e35  add_doc66_indexes_idempotent    ← 补 11 个索引：6.6 的 10 个 + 6.6 之外的 1 个（本次新增）
```

第二条**先查 `information_schema.statistics`，索引已存在就跳过**。
之所以写成幂等版：**云库当前的索引状态无法确认**（隧道不通），
幂等版无论云库现状如何执行都安全。

存在性判断按**列**而不是按**名**：MySQL 会为每个外键自动建索引（`..._ibfk_N`），
与 6.6 点名的 `idx_space_id` / `idx_device_id` 名字对不上；只比名字会在同一列上
再建一条重复索引。判定口径是「列序列完全相同（含顺序）」，不是「前缀相同」——
前缀判定会让 6.6 点名的索引在 `SHOW INDEX` 里彻底消失，反而制造「索引缺失」的误判。
详见 `docs/database.md` 3.1 与 3.4。

`downgrade` 也做了存在性预检：MySQL 的外键自动索引名与目标名不一致，
直接 `DROP INDEX` 会报 `Can't DROP`。

> ⚠️ `--sql`（离线）模式下降级为**无条件的 `CREATE INDEX`**（离线模式拿不到
> `information_schema`）。所以离线生成的 SQL **不能直接拿去线上执行**，
> 它只用于评审。有测试 `test_offline_sql_lists_all_migration_indexes` 钉住这一点并输出警示注释。

### 7.6 模型 `__table_args__`

模型里补了索引声明（**只加 `__table_args__`，字段定义一律不动**），
作用是**防止下次 `autogenerate` 把那 11 个索引当「多余对象」生成 `drop_index`**。

### 7.7 角色权限的存储

见第 6.1 节。**`sys_permission` 表在种子里刻意留空**（它是前端菜单字典，不参与鉴权），
因此不要指望从它读出权限。

## 八、事务与并发规范

> **这一节有一个会让数据静默丢失的坑，请务必读完。**

### 8.1 `get_db` 只负责关闭，commit 由服务层显式调用（决策 11）

```python
# app/core/database.py
async def get_db() -> AsyncIterator[AsyncSession]:
    async with AsyncSessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback()
            raise
        # ★ 这里没有 commit
```

**为什么**：`开发流程.md` 5.5 要求「事务边界由服务层控制」。
若 `get_db` 自动 commit，会出现两个问题：
① 一次请求里的多个写操作被拆成多个事务，无法保证原子性；
② 「业务异常不该提交」这件事会变得依赖异常类型的细节，很难推理。

### 8.2 代价：忘写 `commit()` 会**静默丢数据**

**这是本项目最危险的一类 bug**：接口返回 200、日志正常、没有任何报错，
但数据没进库。原因：SQLAlchemy 的 `flush()` 会把 INSERT 语句发到数据库，
**但它在一个未提交的事务里** —— 会话关闭时事务回滚，写入消失。

**防线**：`tests/integration/test_db_session_contract.py`（5 个用例，标 `db`）。

> ⚠️ **为什么这个坑需要专门的测试**：`app/services/auth_service.py` 整条链路**不写库**
> （登录只读、续期只读、登出只动 Redis），所以**认证接口的测试永远覆盖不到事务边界**；
> 而且接口测试用 `dependency_overrides` 替换了 `get_db`，
> 导致**生产的 `get_db` 本体一次都没被执行到** —— 就算有人给 `get_db` 加上 `commit()`，
> 也不会有任何用例失败。
>
> 该测试改为 monkeypatch `AsyncSessionLocal`，让**本体真的跑起来**，
> 并用**另一个引擎的连接**来观察（用同一个会话验证「提交了没有」是无效的 ——
> 未提交的数据在自己会话里一定看得到）。

### 8.3 并发控制

`开发流程.md` 5.5 要求预约等场景用 `SELECT ... FOR UPDATE` 防重复预约。
**SQLite 没有这个语义**，因此：

- 自动化测试**测不到**行锁行为（已如实记在 `docs/test.md` 5.6 的未覆盖清单）；
- 必须在**云库上人工验证**，步骤见 `docs/deploy.md` 4.5 第 7 项。

时间区间重叠判定（模块 3 会用）：

```python
# 开区间：start < :end AND end > :start
```

### 8.4 ORM 字段定义已冻结

`app/models/*.py` 的**字段定义一律不得改动**（决策 10）——本轮只为它们补了 `__table_args__`。

原因：模型声明的是 `BIGINT`（signed），云库实际是 `BIGINT UNSIGNED`，两者长期不一致。
但改模型会牵动已建表、已有数据与全组的类型假设，
**收益（消除 autogenerate 噪音）远小于风险**。
改用「`env.py` 里忽略该差异 + 文档说明原因」的方式处理。

> 后人若想「顺手修正」这个不一致，请先读 `docs/database.md` 第五节。
> 这是**知情的取舍**，不是遗漏。

### 9.3 marker 使用

| marker | 含义 |
| --- | --- |
| `unit` | 纯逻辑，不涉及数据库与网络 |
| `api` | 通过 ASGI 客户端调用（SQLite + 假 Redis） |
| `db` | 直接驱动 `get_db` 的契约测试，不经过 HTTP |

| `integration` | **需要真实外部依赖**（已注册，当前无用例） |

> ⚠️ **新文件必须加 `pytestmark`**。本轮发现 `tests/unit/test_metrics.py` 与

> **静默跳过**这 33 个用例 —— 看起来「通过了」，其实根本没跑。
> 已修复，现在 `-m unit` 收集 178/349 项（与逐文件统计一致）。

### 9.4 已知限制要「钉住」而不是「静默修掉」

本项目的已知限制（时区不换算、宽限期可复活已登出的会话、500 无 CORS 头等）
都用**带 ⚠️ 说明的断言**钉住了。

**为什么**：这些都是**跨模块契约或框架结构**决定的行为。
静默「顺手修掉」会让前端按旧假设写好的代码在联调当天失效；
而钉住 + 写进待确认项，能让「当前行为是什么」有据可查、改动时有测试报警。

| 存活探针 | `GET /health` | **恒 200**，不检查任何依赖 |
| 就绪探针 | `GET /ready` | **恒 200**，返回 `db`/`redis` 状态供诊断 |
| 指标查询 | `GET /monitor/agent` | `totalCalls` / `successRate` / `avgLatency`（**秒**，1 位小数） |

**`SQL_ECHO` 与 `DEBUG` 刻意解耦**：默认 `false`。
开启后 SQLAlchemy 会把 SQL 与参数打进日志，**其中包含 `sys_user.password` 的 bcrypt 哈希** ——
开发日志经常被粘贴到群里求助，所以默认必须关。

### 10.1 埋点绝不影响业务（重要设计）

`agent_metrics.py` 与 `metrics.py` 的**所有** Redis 操作：

- 异常全部吞掉（只记 WARNING）；
- 用 `REDIS_SOCKET_TIMEOUT=0.5` 的短超时；
- 读失败时回落到内存镜像，且**不低估**已有计数。

有回归测试钉住：**埋点抛异常时业务接口仍返回 200**
（`test_broken_metric_store_does_not_break_business_endpoint`）。

**为什么投入这么多**：模块 4 的 Agent 链路是答辩演示的主角。
如果埋点因为 Redis 抖动抛异常，整个业务接口 500 —— 那是本末倒置。

## 十一、分支、提交与 CI

> `开发流程.md` 第 8 章。**注意**：本轮开发**没有执行任何 git 命令**（决策 14），
> 因此以下规范由各成员在自己提交时执行。

### 11.1 分支

| 分支 | 用途 |
| --- | --- |
| `main` | 生产稳定分支，仅通过 PR 合并 |
| `develop` | 开发集成分支 |
| `feature/<module>-<name>` | 功能分支，如 `feature/auth-shenyunfei` |

分支名**禁止使用中文**。

### 11.2 提交信息

格式 `<type>(<scope>): <subject>`，type ∈ `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `chore`。

示例：`feat(auth): 实现 refreshToken 轮换与宽限期`

### 11.3 推送前检查

```
[ ] .env 未被提交（.gitignore 已覆盖）
[ ] requirements.lock 已同步（改依赖时）
[ ] commit message 符合规范
[ ] 本地测试通过
[ ] 先 pull 再 push
```

### 11.4 CI 与 pre-commit 的位置（2026-09-28 已修复）

两者原先都放在 `backend/` 下（`backend/.github/workflows/ci.yml`、
`backend/.pre-commit-config.yaml`），**因此都不能生效**：

- **CI**：GitHub Actions 只扫仓库根目录的 `.github/workflows/**`，放 `backend/` 下等于没配。
  这条流水线**一次都没跑过**。
- **pre-commit**（更重要）：它只认 git 根及祖先目录下的配置，`backend/` 下的那份
  **不会被加载**；而规则里的 `files:` 匹配的是**相对仓库根**的路径。
  于是 `no-secrets-file` 的旧正则（只匹配根目录的 `.env`）既没被加载、写法也漏 ——
  这正是 `.env` 被反复提交（3 次取消跟踪又被加回去）的原因。

现已移到仓库根：`.github/workflows/backend-ci.yml`（加 `working-directory: backend`）
与 `.pre-commit-config.yaml`（所有 `files:` 补 `^backend/` 前缀）。**首次运行前
已把 ruff 告警与格式清理干净**，避免「第一次跑就是红的」。

> `.pre-commit-config.yaml` 里最有价值的一项是 **`no-secrets-file`**：
> `.env` 一旦进过仓库历史，密钥就必须更换（历史无法撤回，且可能已被缓存/索引）。
> 这一项在 CI 里也单独跑一次，且**必须回仓库根执行**。

## 十二、模块 1～8 接入联调指南

> 这是模块 10「系统集成」的核心交付：**别人把接口接进来时要做什么**。

### 12.1 五步接入清单

```
1. 路由注册     app/api/v1/__init__.py 里 include_router          ← 漏了会 404
2. 响应体       出参用 CamelModel，返回 ok(...)                    ← 漏了信封检查会失败
3. 权限门禁     写接口加 Depends(require_permission(...))          ← 漏了是安全漏洞
4. 埋点         无需做任何事（纯 ASGI 中间件自动统计 /agent/*）
5. 测试         正常 + 校验失败 + 未鉴权 + 权限不足（各 1 条）
```

第 4 步是唯一的「免费」项 —— 中间件让业务代码零改动即获得埋点。

### 12.2 三类护栏（漏了会被拦下）

| 护栏 | 拦什么 | 位置 |
| --- | --- | --- |
| 信封遍历测试 | 接口忘了包统一响应体、或返回了非 camelCase 字段 | `tests/api/test_response_envelope.py` |
| 未登记路径检查 | 有非 `/api/` 路径没登记进 `EXEMPT_PATHS`（登记即审查） | 同上 |
| Mock 一致性检查 | `MOCK_CALLS` 表与实际注册的 Mock 路由不一致 | `tests/api/test_mock_routes.py` |

### 12.3 联调期的 Mock 路由

模块 1～8 尚未实现时，前端可先用 `/mock/*` 并行开发：
**21 个接口**，覆盖模块 1/2/3/5/6/7/8 的主要契约，返回静态示例数据。

- **仅 `DEBUG=true` 时注册**（`开发流程.md` 8.8），生产必须 `DEBUG=false`；
- `POST /mock/simulate` 可灌入指定数量的 Agent 流量，让 `/monitor/agent` 显示真实统计
  （演示模块 8 大屏时用）；
- `/mock/agent/schedule?degraded=true` 会带上 `X-Agent-Degraded: 1`，用于演示**降级路径**。

**Mock 接口的完整表格见 `docs/api.md` 3.4。**

### 12.4 从前端视角的联调清单

`docs/api.md` 第八节列了 10 项（camelCase、时间格式、按 code 分支、
`X-Request-Id`、单例 Promise 去重刷新、`data.errors` 结构……）。**前端联调前请转给他们。**

## 十三、陷阱与已知限制汇总

### 13.1 陷阱（会让人浪费时间的）

| # | 陷阱 | 表现 | 规避 |
| --- | --- | --- | --- |
| 1 | **`get_db` 不自动 commit** | 接口 200 但数据没进库，**无任何报错** | 服务层显式 `await db.commit()`（第 8 节） |
| 2 | `python -m alembic` | `No module named alembic.__main__` | 用 `alembic` 命令（7.2） |
| 3 | `model_dump()` 漏 `by_alias=True` | 成功响应 camelCase、错误响应 snake_case | 用 `ok()`；手写 dict 要显式传 |
| 4 | 新测试文件漏 `pytestmark` | `-m unit` **静默跳过**，看起来通过了 | 每个新文件加 marker（9.3） |
| 5 | `DEBUG=true` 进生产 | 21 个无鉴权 Mock 接口暴露 | 部署清单（`docs/deploy.md` 5.5） |
| 6 | `REDIS_ENABLED=false` + `--reload` | 改一次代码所有人掉线 | 联调用 `RELOAD=0`（2.4） |
| 7 | 多 worker + 内存白名单 | 登录后请求被负载到别的 worker 就 401 | 生产必须启用 Redis |
| 8 | Nginx `client_max_body_size` 与后端上限不一致 | 大文件被 Nginx 413 拒，**后端错误处理执行不到** | 两处对齐（`docs/deploy.md` 5.3） |
| 9 | 前端传带时区的 ISO 时间 | 8 小时偏差 | 要求传 `YYYY-MM-DD HH:mm:ss`（4.4） |
| 10 | 把权限写成只差后缀 | `order:view_all` 不含 `order:view` | 精确匹配（6.3） |
| 11 | 把库里的 `permissions` 改成非空子集 | 该角色**只剩这些**权限（不叠加静态清单） | 知情的回落规则（6.4） |
| 12 | 离线 `--sql` 生成的迁移直接上线 | 索引已存在时会报错（离线版是无条件建） | 离线 SQL 只用于评审（7.5） |
| 13 | `.env` 的 `DB_PORT` 填成云库真实端口 | 连不上 | 开发机填**隧道本端**端口（`docs/deploy.md` 2.2） |
| 14 | 短 `JWT_SECRET_KEY` | dev 下仅警告，能跑起来但可被伪造令牌 | ≥32 字符随机值（`docs/deploy.md` 3.1） |

### 13.2 已知限制（**都有测试钉住，改动前请先看测试**）

| # | 限制 | 影响 | 真实修法 |
| --- | --- | --- | --- |
| 1 | **登出后 accessToken 仍可用到过期** | `.env` 当前 `JWT_EXPIRE_MINUTES=1440`，即最长 24 小时（文档设计的 30 分钟则是最长 30 分钟） | 令牌加 `sid` 声明，白名单按会话校验（跨模块 JWT/Redis 契约变更） |
| 2 | **宽限期内可复活已登出的会话** | 登录→A、续期→B、登出、重放 A 仍得 200 | 同上，`sid` 可解决 |
| 3 | 带时区的时间输入不换算 | 8 小时偏差 | 前端只传本地格式；或后端统一换算（需全组同意） |
| 4 | 框架级未处理异常的 500 无 CORS 头与 `X-Request-Id` | 前端拿不到任何上下文 | Starlette 的 `ServerErrorMiddleware` 在最外层，属框架结构；需自定义最外层中间件 |
| 5 | 72 字符 ≠ 72 字节（bcrypt 截断） | 长密码的第 72 字节之后不参与校验 | 无（bcrypt 的固有特性），登录不做长度策略以避免历史账号无法登录 |
| 6 | `get_db` 的 `except Exception` 不捕获 `CancelledError` | 取消路径不走回滚分支 | 实际安全性由 `AsyncSession.close()` 保证（已用测试确认数据不落库）；这是 Python 3.8+ 的语义 |
| 7 | `integration` marker 无用例 | 真库层面的验证缺失 | 云库可达后补 |
