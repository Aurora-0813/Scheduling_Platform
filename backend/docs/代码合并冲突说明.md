## 1. 拉取过程：GitHub HTTPS 不可达及其绕行

这一步本身也是本次合并的一个"坑"，记录下来供后续同学参考。

### 1.1 现象

```
$ git clone https://github.com/Aurora-0813/Scheduling_Platform.git
# 卡约 21 秒后失败：Failed to connect to github.com port 443: Timed out
```

`GIT_CURL_VERBOSE=1` 显示 TCP 握手阶段就超时，DNS 解析正常
（`github.com` → `20.205.243.166`），且 `pypi.org`、`api.github.com` 均正常可达。

### 1.2 定位

逐个探测 GitHub 相关域名的可达性，得到关键线索：

| 域名 | 解析 IP | 结果 |
| --- | --- | --- |
| `github.com` | 20.205.243.166 | ✗ 000（握手超时） |
| `gist.github.com` | 20.205.243.166 | ✗ 000 |
| `api.github.com` | 20.205.243.168 | ✓ 200 |
| `codeload.github.com` | 20.205.243.165 | ✓ 301 |
| `objects.githubusercontent.com` | 185.199.108.133 | ✓ 404（服务正常） |

**四个域名同属 GitHub，却只有 `github.com` / `gist.github.com` 不通 ——
说明封锁是针对 IP（20.205.243.166）而非针对域名或整个网段。**

> 注：本机是非管理员账户，**无法修改 hosts 文件**来绕过 DNS。

### 1.3 两次尝试

1. **本地 CONNECT 代理**（`gh_proxy.py`，仅监听 `127.0.0.1:8899`，把 GitHub 域名
   重写到可达的边缘 IP，保留 SNI 与证书校验）。当时探测到 `140.82.112~116.x`
   可用，克隆成功。**但本次合并后期这批 IP 也转为不可达**，代理随之失效。
2. **改用 codeload 直接取 tarball**（最终方案，不依赖 `git` 与 `github.com`）：

   ```bash
   curl -L -o repo.tar.gz \
     https://codeload.github.com/Aurora-0813/Scheduling_Platform/tar.gz/refs/heads/main
   ```

### 1.4 结论 / 建议

- 本网络下**按 IP 的封锁是动态的**，同一 IP 今天通、明天可能不通。
- 仓库 `.env.example` 里"推送一律走 SSH（`ssh.github.com:443`）"的说法**方向正确但不够完备**：
  本次实测连 `github.com:443` 本身都不通，而 `codeload` 可用。
- **推荐的取代码顺序**：
  1. `git clone`（配好 SSH over 443）—— 首选；
  2. 不通则 `curl` codeload tarball —— 只读、无需认证、本次已验证可行；
  3. 都不通再考虑本地代理方案。
- 上述内容已补记到 `.env.example` 末尾的备忘段。

## 2. 假冲突：行尾符（CRLF / LF）

初次比对时，`diff` 报出 28 个文件"全文件冲突"。逐个核查后发现其中相当一部分
**唯一差异是行尾符** —— 远端在 Windows + PyCharm 下提交了 CRLF，
本地是 LF（`.gitattributes` 未约束行尾符）。

处理方式：所有比对统一改用 `diff --strip-trailing-cr`，
把"假冲突"从 28 个降到 23 个真正需要判断的文件。

**建议（遗留项）**：在仓库根加 `.gitattributes` 强制 `* text=auto eol=lf`，
从根上消除这类噪音。

## 3. 真正的语义冲突与解决

### 冲突 1：数据库引擎 —— 同步（pymysql） vs 异步（asyncmy）★影响最大

| | 远端 `backend/` | 本地 |
| --- | --- | --- |
| `app/core/database.py` | 同时维护 `sync_engine`（`create_engine` + **pymysql**）与 `async_engine` | **仅有 `async_engine`**，同步引擎已删除 |
| `alembic/env.py` | `engine_from_config`（同步），读 `settings.sync_database_url` | `async_engine_from_config` + `connection.run_sync()`（全异步） |
| `requirements.txt` | `pymysql==1.1.1`、`alembic==1.13.3` | 无 pymysql、`alembic==1.20.0` |

**冲突点**：项目文档 3.4 **明确禁止同步驱动**，连接串固定 `mysql+asyncmy://`。
远端保留的同步引擎是早期实现，本地已在后续改造中移除并改为全异步迁移。

**解决：采用本地（异步）**，理由：

1. 文档 3.4 是硬约束，保留 pymysql 会与其直接矛盾；
2. 本地 `alembic/env.py` 已改造为异步且 `tests/integration/test_migrations.py`
   已在该实现上跑通；
3. 全仓 grep 确认本地**已无任何** `pymysql` / `sync_engine` / `sync_database_url` 引用
   （仅 `create_async_engine` 中含 "sync" 子串），因此不存在"删了引擎却还有代码在用"的风险。

**连带处理**：
- `.env.example` 中提及 `settings.sync_database_url` 的两处说明已删除/改写；
- `requirements.txt` 末尾追加「合并记录」段落，写明**不采纳 pymysql** 及理由。

### 冲突 2：业务错误码与 HTTP 状态码约定 ★需集成组最终确认

| | 远端 `backend/`（模块 1/2 开发期） | 本地（模块 9/10） |
| --- | --- | --- |
| HTTP 状态码 | **恒 200**，错误只体现在 `code` 字段 | **真实状态码**（400/401/403/503…） |
| 业务错误码 | 裸码，如 `400`、`401`、`41001`、`41002` | 5 位分段：`40001`、`40101`、`40102`… |

这是**唯一一处无法靠"远端过旧"解释的、方向性不同的设计**。远端代码顶部注释
自述为"临时方案，待集成组确认"。

**解决：以本地的「真实 HTTP 状态码 + 5 位业务码」为准**，同时**为模块 1/2 保留
兼容层**，使其代码不必改写即可运行：

1. `app/core/response.py` 新增两个兼容函数：
   ```python
   def success(data=None, message="操作成功") -> dict          # 等价 ok()
   def fail(code, message=None, data=None) -> dict             # 等价 error_payload()
   ```
   模块 1/2 的路由层用的是 `success(...)` / `fail(code=..., message=...)`，
   现在可直接工作。

2. `app/core/exceptions.py` 新增 `BusinessError(code, message, data)` 兼容类
   （继承本地 `BizError`），并新增业务码 → HTTP 状态码映射表：
   ```python
   _BUSINESS_ERROR_HTTP_STATUS = {
       IMAGE_TYPE_UNSUPPORTED: 400,
       IMAGE_TOO_LARGE:        400,
       AI_MODEL_UNAVAILABLE:   503,
   }
   ```
   未登记的业务码默认映射到 400。

3. `app/core/error_codes.py` 新增 **41xxx 段**（感知类模块专用）：
   `IMAGE_TYPE_UNSUPPORTED=41001`、`IMAGE_TOO_LARGE=41002`、`AI_MODEL_UNAVAILABLE=41003`，
   并补齐 `DEFAULT_MESSAGES`。

> **⚠️ 待确认**：若集成组最终决定**改回"HTTP 恒 200"**，需要改动的是
> `response.py` 的 `_json_response` 调用处与 `BusinessError.http_status` 映射，

### 冲突 3：路由前缀重复（若不修会直接 404）★已修

远端模块 1/2 的 router 写的是**完整前缀**：

```python
router = APIRouter(prefix="/api/v1/image", tags=[...])   # 远端
router = APIRouter(prefix="/api/v1/voice", tags=[...])   # 远端
```

它们当时挂在各自的临时 `main.py` 上，因此是全路径。但本地的
`app/api/v1/__init__.py` 已经用 `app.include_router(api_router, prefix=API_V1_PREFIX)`
把汇总 router 挂在 `/api/v1` 下。

**两个叠加会得到 `/api/v1/api/v1/image/analyze` —— 全部 404。**

**解决**：改为相对前缀，并在文件顶部写明原因：

```python
router = APIRouter(prefix="/image", tags=["摄像头空间感知（模块 2）"])
router = APIRouter(prefix="/voice", tags=["语音输入（模块 1）"])
```

**已验证**：`app.routes` 中不存在任何含 `/api/v1/api/v1` 的路径，
实际注册为 `/api/v1/image/{analyze,sketch}` 与 `/api/v1/voice/{asr,format}`。

### 冲突 5：`AUTH_BYPASS` 开关 —— 要不要在本地实现？

远端模块 1/2 的**接口与测试都依赖**这个开关，但本地 `deps.py` 里**原本没有它**。

**解决：实现它，但加三道保险**（这也是模块 1/2 的测试能跑通的前提）：

1. **仅 `APP_ENV=dev` 生效** —— 非 dev 环境在 `config.py` 启动校验阶段直接拒绝启动；
2. **每次放行都打 `WARNING` 日志**，避免"忘了关"却无人察觉；
3. **放行的身份取通配符权限 `*`**（等同管理员），语义明确，不叠加权限判定制造困惑。

> **⚠️ 注意**：合并前模块 1/2 的测试依赖开发者本地 `.env` 里**恰好写着
> `AUTH_BYPASS=true`** 才能通过。这会让"用例是否通过"取决于机器上的私有配置

### 5.3 合并初期 14 个失败用例（全部在模块 1/2 的测试文件）及修复

初次运行有 **14 个失败**，全部集中在 `tests/test_image_api.py`（10）与
`tests/test_voice_api.py`（4）。根因是**两类**，都属于"测试按临时环境的约定写死了"：

**根因 A：测试依赖本机 `.env` 里的 `AUTH_BYPASS=true`（12 个失败）**

| 文件 | 修复 |
| --- | --- |
| `tests/test_image_api.py` | `make_client` 夹具中显式 `monkeypatch.setattr(settings, "AUTH_BYPASS", True)` |
| `tests/test_voice_api.py` | 新增 autouse 夹具 `_auth_bypass` 做同样的事 |

**根因 B：断言的是"HTTP 恒 200"与模块开发期的错误码/字段名（其余失败）**

| 用例 | 原断言 | 改为 | 依据 |
| --- | --- | --- | --- |
| `test_missing_token_returns_401` | HTTP 200 + `code==401` | HTTP **401** + `code==40101` | `TokenMissingError` |
| `test_malformed_auth_header_returns_401` | `code==401` | HTTP 401 + `code==40101` | 缺 Bearer 前缀 ⇒ 按"缺令牌"处理 |
| `test_invalid_token_returns_401` | `code==401` | HTTP 401 + `code==40102` | `TokenInvalidError` |
| `test_missing_file_returns_friendly_error` | `code==400`、`data is None` | HTTP 400 + `code==40001`、`data["errors"]` 非空 | 参数校验失败经全局处理器 |
| `test_unsupported_image_type_returns_41001` | HTTP 200 | HTTP **400** + `code==41001` | 业务码→HTTP 映射 |
| `test_format_missing_field`（voice） | HTTP 200 + `code==400` | HTTP 400 + `code==40001` | 同上 |
| `test_health_check` | `data["app"]` | `data["status"]/["service"]/["env"]` | 以模块 10 `health.py` 的字段为准 |

**`test_valid_token_is_accepted` 需要重写（原写法在本项目下测不到"放行"）**

原用例手写了一个 JWT，载荷是 `{userId, username, role, exp}`。但本项目
`decode_token` 要求的是 `{sub, type, jti, iat, exp, ver}`（RFC 7519 的 `sub`，
外加用于区分 access/refresh 与支持强制下线的 `type`/`jti`）。
**按原载荷签发的令牌，在本项目里就是一枚"结构不符的伪造令牌"，必然得到 40102。**
此外 `get_current_user` 验签后还要查库取角色与状态，而该文件其他用例把 `get_db`
换成了返回 `None` 的会话，查库必失败。

改写为：令牌由项目自身的 `create_token()` 签发 + `monkeypatch` 掉
`auth_service` 的 `get_user_by_id` / `role_name_of` / `permissions_of` 三个函数。
**这样测的才是"合法令牌被放行"这条路径。**

### 5.4 另外发现并修复的本地既有缺陷（1 个，**非合并引入**）

`tests/api/test_auth_api.py::test_info_with_forged_signature_returns_40102`
是**本组原有的、会随机失败**的用例（约 **1/16 ≈ 6.25%** 概率）。本次验证恰好撞上。

**原因**：用例用"篡改签名最后一个字符"来伪造令牌：

```python
tampered = forged[:-1] + ("A" if forged[-1] != "A" else "B")
```

HS256 签名是 32 字节，base64url 编码后 43 个字符，**末字符只承载 4 个有效比特**
（低 2 位是补位，解码时被丢弃）。因此当末字符恰好是高位为 `0000` 的那类字符
（实测只有 `'A'`）时，改成 `'B'` 解码出的**签名字节完全不变**，令牌依然有效 ⇒
断言 `status_code == 401` 失败。

实测统计（2 万次采样）：末字符为 `'A'` 的比例 **6.33%**，与理论值 1/16 吻合。

**修复**：改为篡改签名的**第一个**字符（6 个比特全部参与解码，改掉必然验签失败）：

```python
head, body, signature = forged.split(".")
tampered = f"{head}.{body}.{'A' if signature[0] != 'A' else 'B'}{signature[1:]}"
```

修复后连续运行 **25 次全部通过**。

> 这个缺陷与本次合并无关，但因为它会让"测试是否全绿"取决于运气，
> 已一并修掉并在此记录。
